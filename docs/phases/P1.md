# P1 — Core loyalty

**Goal:** the heart of the product, at production standard: scan → join → request → approve → gold pours → rewards → redeem. Points and rewards represent real value for shops and customers, so the loyalty engine is pure, exhaustively tested, and its invariants are enforced by database constraints, not only code.

**Target date:** Mon 30 Nov 2026 (plan v5 re-baseline; assumptions in PHASES.md and PROGRESS).

## How to work this phase
- **Before the first task of this phase**, run a brief review: fill any missing Edge cases and measurable Acceptance criteria in this file (one agent, cheap; commit with the first task).
- **Self-verification is part of every task:** test first for logic, run the app, inspect screenshots, try to break it (TESTING §7–8).
- **Task:** `pnpm gate:task` only (check + test:int + build + the task's E2E specs on the production build, Chromium + WebKit). No full regression, no exploratory QA agent, no all-project runs. Tasks on the security-relevant list (CLAUDE.md §4) run `security-reviewer` on the task diff before the tick. Tick only with evidence for every acceptance criterion.
- **Sub-phase close (`/subphase-complete`) is light:** CI green on the last commit (CI already ran the full suite; do not re-run it locally); staging deploy + smoke + Sentry check; `code-reviewer` (+ `security-reviewer` for server/auth code, `design-reviewer` for UI) on commits not already reviewed at task tick; exploratory QA only if the sub-phase added or changed screens, scoped to those screens at 320/390/1440 on Chromium + WebKit; update PROGRESS + HUMAN_TASKS; push.
- **Phase close is the one heavy gate:** `pnpm gate:phase` + definition of done + demo. P1-18 IS that run; `/phase-complete` does not repeat it. Demo for P1: screenshot walkthrough of the Demo 2 script (no recorded rehearsal).
- Sub-phases A → D in order. Read CLAUDE.md, ENGINEERING §1, §4–8, and each task's **Read** list.

## Sub-phase P1-A · Shops and entry

### P1-01 · Shop entities, codes, hours, NFC records
**Depends on:** P0 complete.
**Read:** PRODUCT §3, §4, §14 (Settings), §19; ARCHITECTURE §4 (shops, shop_hours, shop_closures, nfc_tags).
**Build:**
- Migrations: remaining `shops` columns, `shop_hours` (weekday, opens, closes; supports overnight), `shop_closures` (date, note), `nfc_tags` (tag_uid, status, replaced_by).
- Shop code generation (6 chars, Crockford base32) with uniqueness and retry; stored upper-case; lookup case-insensitive.
- QR service: SVG + PNG for `https://<APP_URL>/s/<code>?src=qr` (error correction level M, quiet zone 4); NFC URL `?src=nfc`.
- `openStatus(shop, hours, closures, now)` pure service → `open | closes_soon (≤30 min) | closed | opens_at(time)`; Europe/London; overnight windows; closures override hours.
- Builders: Google Maps directions URL from lat/lng; `tel:` link from E.164.
**Acceptance criteria:**
- (CARRIED C-34 from P0-20 review) Migration checker (and catalog test) fails a `moz_app` policy of `USING (true)` / `WITH CHECK (true)` without a `-- rls: open <table> — <reason>` marker, and a `-- rls: global` marker only counts in the migration that creates the table; admin cross-shop reads can only go through `adminRead` (type or lint guard); customers can't write `memberships` counters (column grants).
- `openStatus` correct for: normal day, overnight (18:00–02:00) before/after midnight, closure day, no hours set, the BST start and end dates, closes-soon boundary at exactly 30 min.
- Concurrent shop creation never duplicates codes (constraint + retry).
- QR decodes to the exact URL (decode test).
**Tests:** ≥ 12 unit cases for `openStatus`; QR decode test; code uniqueness integration test.
**Edge cases:** code generation retries exhausted (fails loudly with an alertable error, never a duplicate or a shorter code); lookup with lower case or surrounding spaces (normalised; ambiguous characters `0/O/1/I/L` never generated, so a mistyped one is simply "not found"); overnight window ending inside a closure day (the closure wins from midnight); hours set to the missing hour on the BST start date (treated as opening at 02:00); NFC tag replaced twice (each old tag redirects to the current one, no chain longer than one hop).
**Verify:** test output.

### P1-02 · Shop landing page `/s/[code]`
**Depends on:** P1-01.
**Read:** PRODUCT §3; DESIGN §5, §12, §15 screen 1; reference `m01`/`d01`; ARCHITECTURE §5 (Scan → landing), §12.
**Build:**
- Server Component page rendered per request with the per-request nonce CSP. HTML is never CDN-cached (`Cache-Control: private, no-store`); the CDN caches only static assets and `cdn.` images. The public shop data (profile, hours, closures, reward preview) is cached in `redis-cache` for 60 s keyed by shop code, invalidated on shop update or status change, and holds nothing user-specific; personalised state (joined, progress) is read separately per request and never written to that cache.
- Content per screen 1: cover with ivory fade, overlapping logo, name, category · area, open status, primary "Collect points", secondary "Rate your visit" and "Today's offer" (hidden until P3 provides data), reward preview with static ingot, shop details (hours, address, map thumbnail on desktop), footer with "Powered by Moz Rewards", terms and privacy links.
- Desktop: split hero (cover left, details + CTAs right) per screen 1.
- States: unknown code (designed 404, no DB hit for invalid format), suspended shop (friendly message, `noindex`), closed shop ("This shop is no longer on Moz Rewards"), restricted plan (landing works normally).
- Metadata: title, description, Open Graph image (cover), canonical URL; `src` parameter used for analytics only.
- CSP and caching (plan v5, B1): never CDN-cache HTML. A hash-based CSP is not workable with the App Router (the inline RSC payload scripts change with the page's data), so this route, like every other, uses the per-request nonce CSP; the same rule applies to the offers feed (P3-05). Record the decision in DECISIONS (supersedes the v4 hash-CSP entry).
- Shop-code lookup protection (closes CARRIED C-15): per-IP Redis sliding-window limit on `/s/[code]` lookups (default 60 / min / IP; friendly 429 page with `Retry-After`) — our limit is the real control; a Cloudflare free-plan rate-limit rule on `/s/*` is the backstop only.
**Acceptance criteria:**
- Mobile Lighthouse (throttled): LCP ≤ 2.5s, CLS ≤ 0.05, initial JS ≤ 130 KB gzip (judgment rule).
- The `redis-cache` entry contains no personal data (test reads the cached value after a signed-in and an anonymous visit and finds no user id, name, membership or progress); the signed-in HTML is never served to an anonymous request.
- HTML response carries the nonce CSP with a different nonce on two consecutive requests, no `'unsafe-inline'` for scripts, and `Cache-Control` forbidding shared caching; the page loads on the production build with zero CSP violations in the console.
- A second request within 60 s reads the shop data from `redis-cache` (no shop query; query counter); a shop update or status change invalidates it at once; `redis-cache` down → the page renders from the database (public data fails open).
- The 61st lookup from one IP within a minute gets 429 with `Retry-After`; the limit is keyed on the trusted client IP (TRUSTED_PROXY), not a spoofable header.
- Layout matches screen 1 on mobile and desktop.
**Edge cases:** missing cover/logo (designed fallbacks), 60-character names, no hours, no Google Place ID; many requests for the same code on a cold cache (single-flight, one DB read); shop suspended while cached (invalidated; worst case 60 s); unknown-code scan bursts (limited without a DB hit).
**Tests:** E2E for active / unknown / suspended / closed; CSP header test (nonce differs per request on this route, no shared-cache headers on HTML) with the console guard catching violations; integration for cache hit / miss / invalidation / Redis-down and the lookup rate limit; Lighthouse CI entry for this route.
**Verify:** screenshots m/d on Chromium + WebKit; Lighthouse numbers; `design-reviewer` pass.

### P1-04 · Join flow, profile completion, member ID
**Depends on:** P1-02, P0-06.
**Read:** PRODUCT §3, §17; SECURITY §7; COMPLIANCE §2, §3, §7; ARCHITECTURE §4 (customer_profiles, memberships).
**Build:**
- "Collect points" → sign-in if needed (return URL to the shop) → membership upsert (idempotent) → profile completion if incomplete → shop page with a first-join welcome state showing the member ID card.
- Profile form: full name; UK mobile (libphonenumber validation, stored E.164, AES-256-GCM encrypted with key id, HMAC blind index); birthday day + month (optional, explained); per-shop marketing opt-in stored as `membership.marketing_opt_in` (default false, asked at join, unticked, clear wording, timestamped consent record); 13+ confirmation.
- Keys: the field-encryption data key (with key id) and the blind-index key are separate keys, never derived from another secret. Key rotation: a new data key id becomes current for writes; a re-encryption job rewrites existing ciphertext under the current key id in keyset batches (idempotent, resumable, audit-logged). Rotation steps go into RUNBOOK.
- Member ID generated once (`XXX-XXX`), immutable.
**Acceptance criteria:**
- The phone blind index uses `purposeKey("blind-index")` (HKDF subkey, src/server/security/keys.ts), never `BLIND_INDEX_KEY` directly (SECURITY §7, P0-19 decision).
- Re-scanning a joined shop never creates a second membership.
- Phone stored as ciphertext; plaintext never logged or returned to anyone but the owner of the profile and that shop's authorised staff (masked by default).
- Consent stored per membership with timestamp and wording version; `marketing_opt_in` is false unless the customer ticked it.
- After rotation, new writes carry the new key id, old rows still decrypt, the re-encryption job leaves zero rows on the old key id, a second run changes nothing, and blind-index lookups still match.
**Edge cases:** abandoning the profile form (resumes next visit); international numbers (rejected with UK-only message unless DECISIONS says otherwise); joining a suspended shop (blocked with message); joining while the shop's plan is restricted (allowed); re-encryption job interrupted mid-batch (resumes without double-encrypting); unknown key id (fails loudly, never returns garbage).
**Tests:** integration: join idempotency (parallel calls), encryption round-trip, blind-index lookup, consent record, key rotation + re-encryption job (interrupt and resume); E2E journey 1.
**Verify:** E2E on Chromium + WebKit; DB inspection shows ciphertext and key ids before/after the re-encryption job.

### P1-06 · Loyalty engine (pure services)
**Depends on:** P1-05.
**Read:** PRODUCT §5, §6, §10 (happy hour), §19; ENGINEERING §7–8.
**Build:** pure functions with explicit inputs and `now`:
- Progress model: progress = sum of the customer's ledger gold in the current ingot; when progress reaches `ingot_size` the ingot fills, `ingots_completed` increments and the reward unlocks; an unlocked reward is never revoked.
- `calculateAward({ program, amountPence, requestedAt, multipliers, streakState })` → points (per-visit or floor(pence/100 × rate)), applied multiplier, streak bonus. Multipliers stacking multiply, rounded down to whole gold after stacking (default — client to confirm).
- `applyAward(state, award, program)` → new progress, ingots completed (can be > 1), overflow carried, milestones crossed (each only once per ingot; milestones repeat every ingot), tier, streak state; any recorded shortfall is offset first.
- `applyReversal(state, gold)` → reduces current-ingot progress only, floored at 0; the remainder is recorded as a shortfall on the membership that offsets future earns; completed ingots and unlocked rewards untouched.
- `estimateVisitsToNext(state, history)`; `computeExpiry(state, program, lastApprovedVisitAt, now)` → rolling expiry measured from the last approved visit, removes only current-ingot progress, warning dates 30 and 7 days before.
- Streak = consecutive ISO weeks (Europe/London) with ≥ 1 approved visit (default — client to confirm).
- Types: `Points`, `Pence` branded.
**Acceptance criteria:** deterministic; no I/O; property tests prove progress never negative, gold is conserved across overflow and shortfall, milestones never double-unlock within an ingot, unlocked rewards are never revoked by reversal or expiry.
**Edge cases:** award exactly fills the ingot; award fills two ingots; zero-amount per-visit; rounding down for per-pound; stacked multipliers (1.5 × 2 on 7 gold → 21); streak boundary at the ISO week change in UK time; tier threshold crossed by a multi-ingot award; reversal larger than current progress (shortfall); earn after shortfall; programme version change between request and approval (earn rate and multipliers from the version active at `requestedAt`; ingot size, reward and milestones from the version the current ingot started under).
**Tests:** ≥ 30 unit cases + property-based tests (fast-check); coverage ≥ 95% for the module.
**Verify:** coverage report.

## Sub-phase P1-C · Requests, approvals, realtime

### P1-10 · Realtime (SSE) infrastructure
**Depends on:** P0-07.
**Read:** ARCHITECTURE §7; SECURITY §3.
**Build:**
- `/api/sse/me` and `/api/sse/shop/[shopId]` (authn + authz, origin check), heartbeat every 25s, Redis pub/sub channels `user:{id}` and `shop:{id}`, typed events (`request_created`, `request_decided`, `points_credited`, `reward_unlocked`, `redemption_confirmed`, `notification`), per-user connection cap; client hook with exponential backoff + jitter and full refetch on reconnect; on shutdown the server sends `retry:` with jitter.
- `notifications` table stub (id, user_id, shop_id, type, category `transactional | marketing`, payload with no PII, read_at, created_at; partitioned monthly) and a dispatch interface `notify(tx, recipient, event)` with two channels only: in-app (row + SSE) and email (template from P2-11, placeholder until then). Email is used only for events on the email budget list (ARCHITECTURE §10: sign-in links, staff invites, plan reminders, data-request mails, weekly owner email, auth/security notices); every P1 customer event (request expired, reversal, expiry warnings, programme change) is in-app only (push added by P3-07). It writes the notification row and the outbox row in the caller's transaction; the relay delivers. Used by P1-11, P1-12 and P1-13; P3-07 adds push, preferences and the inbox UI behind the same interface.
**Acceptance criteria:** staff of shop B cannot subscribe to shop A (403); events delivered across two app instances; reconnect refetches state; no memory leak after 1,000 connect/disconnect cycles (integration loop); `notify` never calls a channel inline (a rolled-back transaction leaves no notification, no email, no SSE event); an event not on the email budget list never produces an email outbox row. (CARRIED C-28 from P0-18) On shutdown each open stream gets `retry:` with a jittered delay before it closes (spread across ≥ 5 s for 100 streams), tested.
**Tests:** integration for authz, fan-out, cap, dispatch rollback; unit for client backoff.
**Edge cases:** session expired or revoked mid-stream (stream closed within one heartbeat; reconnect gets 401); Redis restart (subscribers re-attach; clients refetch on reconnect); per-user cap exceeded (oldest stream closed, never a new one refused silently); proxy buffering (Caddy `flush_interval -1` on SSE routes; heartbeat reaches the client); a staff member removed from the shop while subscribed (stream closed on the next event or heartbeat).
**Verify:** integration output; two-tab check on the production build (approve in one, the event arrives in the other) with a screenshot.

### P1-12 · Approve / reject, owner approval, reversals, receipts
**Depends on:** P1-11, P1-06.
**Read:** PRODUCT §5, §11; ARCHITECTURE §4–5; ENGINEERING §7; SECURITY §12.
**Build:**
- Migrations: `ledger_entries` (append-only trigger), `rewards`, `receipts` (per-shop sequential number via counter row locked in the transaction).
- `approveRequest(requestId, { amountPence?, items?, receiptPhotoKey? })`: staff of that shop; server rejects any award where the approver is the customer (self-award); compute points with the engine (rules per P1-06, happy-hour multipliers hook); above the platform absolute cap per single award (default £500 or 500 gold, configurable by super admin) → rejected; above the staff member's per-award limit → status `awaiting_owner` (stays open, expires on the original 24h; owners notified through the P1-10 dispatch interface plus a dashboard badge; push added by P3-07); otherwise one transaction: lock request row, insert ledger entries (`earn`, `bonus_streak`), update membership counters (`purchase_count`, `last_visit_at`, progress, `ingots_completed`), unlock rewards/milestones, create receipt, and write outbox rows for every side effect (receipt PDF, notification, SSE events, fraud checks) — nothing is enqueued directly; audit log.
- Awards from staff to an account seen on the same device (device signal) succeed but are flagged for the fraud monitor.
- `ownerApprove(requestId)` for `awaiting_owner`; `rejectRequest(requestId, reason)` with preset reasons + free text.
- `reverseAward(receiptId, reason)`: owner role, or the awarding staff member within 15 min of their own award; reason required; `reversal` entry reduces current-ingot progress only, floored at 0; shortfall recorded on the membership and offsets future earns; completed ingots and unlocked rewards are never revoked; the customer is notified; audited.

- Minimal approve UI in the dashboard (full requests page in P2).

**Edge cases:** request expired between viewing and approving; customer left the shop meanwhile; programme changed between request and approval; staff deactivated mid-approval; owner approving their own customer account; reversal larger than current progress (shortfall shown to customer); two reversals of the same receipt (second → CONFLICT).
**Tests:** integration for every criterion and edge case (including concurrent approvals, receipt numbering, outbox rows written in the same transaction); authz entries; E2E journey 2.
**Verify:** test output; DB inspection of ledger and receipts.
