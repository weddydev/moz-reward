# P1 — Core loyalty

**Goal:** the heart of the product, at production standard: scan → join → request → approve → gold pours → rewards → redeem. Points and rewards represent real value for shops and customers, so the loyalty engine is pure, exhaustively tested, and its invariants are enforced by database constraints, not only code.

## How to work this phase
- **Self-verification is part of every task:** test first for logic, run the app, inspect screenshots, try to break it (TESTING §7–8). **Close every sub-phase with `/subphase-complete`** (full regression, exploratory QA, reviews, push, CI + staging verification) and the phase with `/phase-complete`.
- Sub-phases A → D in order. Read CLAUDE.md, ENGINEERING §1, §4–8, and each task's **Read** list.
- Tick a task only with evidence for every acceptance criterion. End each sub-phase with `code-reviewer` (and `design-reviewer` for UI, `security-reviewer` for B and C), then update PROGRESS + HUMAN_TASKS, commit, push.

## Sub-phase P1-A · Shops and entry

### P1-01 · Shop entities, codes, hours, NFC records
**Depends on:** P0 complete.
**Read:** PRODUCT §3, §4, §14 (Settings), §19; ARCHITECTURE §4 (shops, shop_hours, shop_closures, nfc_tags).
**Build:**
- Migrations: remaining `shops` columns, `shop_hours` (weekday, opens, closes; supports overnight), `shop_closures` (date, note), `nfc_tags` (tag_uid, status, replaced_by).
- Shop code generation (6 chars, Crockford base32) with uniqueness and retry; stored upper-case; lookup case-insensitive.
- QR service: SVG + PNG for `https://<APP_URL>/s/<code>?src=qr` (error correction level M, quiet zone 4); NFC URL `?src=nfc`.
- `openStatus(shop, hours, closures, now)` pure service → `open | closes_soon (≤30 min) | closed | opens_at(time)`; Europe/London; overnight windows; closures override hours.
- Builders: Google Maps directions URL from lat/lng; `tel:` link from E.164.
**Acceptance criteria:**
- `openStatus` correct for: normal day, overnight (18:00–02:00) before/after midnight, closure day, no hours set, the BST start and end dates, closes-soon boundary at exactly 30 min.
- Concurrent shop creation never duplicates codes (constraint + retry).
- QR decodes to the exact URL (decode test).
**Tests:** ≥ 12 unit cases for `openStatus`; QR decode test; code uniqueness integration test.
**Verify:** test output.

### P1-02 · Shop landing page `/s/[code]`
**Depends on:** P1-01.
**Read:** PRODUCT §3; DESIGN §5, §12, §15 screen 1; reference `m01`/`d01`; ARCHITECTURE §5 (Scan → landing), §12.
**Build:**
- Server Component page. Anonymous HTML cacheable for 60s at the CDN; personalised state (joined, progress) fetched by a small client component or an uncached segment so the cached HTML is never user-specific.
- Content per screen 1: cover with ivory fade, overlapping logo, name, category · area, open status, primary "Collect points", secondary "Rate your visit" and "Today's offer" (hidden until P3 provides data), reward preview with static ingot, shop details (hours, address, map thumbnail on desktop), footer with "Powered by Moz Rewards", terms and privacy links.
- Desktop: split hero (cover left, details + CTAs right) per screen 1.
- States: unknown code (designed 404, no DB hit for invalid format), suspended shop (friendly message, `noindex`), closed shop ("This shop is no longer on Moz Rewards"), restricted plan (landing works normally).
- Metadata: title, description, Open Graph image (cover), canonical URL; `src` parameter used for analytics only.
**Acceptance criteria:**
- Mobile Lighthouse (throttled): LCP ≤ 2.5s, CLS ≤ 0.05, initial JS ≤ 130 KB gzip (judgment rule).
- Cached response contains no personal data (verify by fetching signed in and anonymous and diffing the HTML).
- Layout matches screen 1 on mobile and desktop.
**Edge cases:** missing cover/logo (designed fallbacks), 60-character names, no hours, no Google Place ID.
**Tests:** E2E for active / unknown / suspended / closed; Lighthouse CI entry for this route.
**Verify:** screenshots m/d on Chromium + WebKit; Lighthouse numbers; `design-reviewer` pass.

### P1-03 · Gilded Gate entry animation
**Depends on:** P1-02, P0-10, P0-11.
**Read:** DESIGN §7, §8.1, §9, §13; `emil-design-eng`, `animation-performance`, `mobile-native` skills.
**Build:** lazy-loaded component, triggered only when `src=qr|nfc` and not yet shown for this shop in this browser session (sessionStorage key per shop). SVG gate stroke draw → logo reveal with soft glow → diagonal shimmer + "Welcome to {shop}" → gate expands into the cover (shared element) → content rises with 40ms stagger. Tap anywhere skips to the final state. Reduced motion → 150ms fade. `arrival` sound only if audio is already unlocked. Data fetching starts immediately and never waits on the animation.
**Acceptance criteria:**
- Duration ≈ 1.4s; skip is instant with no layout jump.
- No CLS from the animation; no long tasks > 50ms during it with 4× CPU throttle.
- Chunk ≤ 35 KB gzip; not loaded at all when `src` is absent.
- Doesn't replay on back navigation within the session.
**Tests:** Playwright: plays with `src=qr`, not without; skip; reduced motion; no replay on back.
**Verify:** `review-animations` and `animation-performance` with no blocking findings; frames at 0 / 0.5 / 1.0 / 1.4s on WebKit and Chromium.

### P1-04 · Join flow, profile completion, member ID
**Depends on:** P1-02, P0-06.
**Read:** PRODUCT §3, §17; SECURITY §7; COMPLIANCE §2, §3, §7; ARCHITECTURE §4 (customer_profiles, memberships).
**Build:**
- "Collect points" → sign-in if needed (return URL to the shop) → membership upsert (idempotent) → profile completion if incomplete → shop page with a first-join welcome state showing the member ID card.
- Profile form: full name; UK mobile (libphonenumber validation, stored E.164, AES-256-GCM encrypted with key id, HMAC blind index); birthday day + month (optional, explained); per-shop marketing opt-in (unticked by default, clear wording, timestamped consent record); 13+ confirmation.
- Member ID generated once (`XXX-XXX`), immutable.
**Acceptance criteria:**

- Phone stored as ciphertext; plaintext never logged or returned to anyone but the owner of the profile and that shop's authorised staff (masked by default).
- Consent stored per membership with timestamp and wording version.
**Edge cases:** abandoning the profile form (resumes next visit); international numbers (rejected with UK-only message unless DECISIONS says otherwise); joining a suspended shop (blocked with message); joining while the shop's plan is restricted (allowed).
**Tests:** integration: join idempotency (parallel calls), encryption round-trip, blind-index lookup, consent record; E2E journey 1.
**Verify:** E2E on Chromium + WebKit; DB inspection shows ciphertext.

## Sub-phase P1-B · Loyalty engine, Wallet, Vault

### P1-05 · Loyalty programme model and basic settings
**Depends on:** P1-01.
**Read:** PRODUCT §6; ARCHITECTURE §4 (loyalty_programs).
**Build:** versioned `loyalty_programs` (immutable versions; new version on every change with `active_from`); templates (Café classic, Restaurant, Retail, Beauty) with sensible defaults; owner-only settings page: earn mode/rate, ingot size, main reward, milestones (≤ 3 at 25/50/75 with mystery flag), streak (window days + bonus), tier thresholds, points expiry (off or ≥ 12 months); live preview with the Ingot component (static until P1-08).

**Tests:** unit validation; integration: change mid-progress keeps balances and rewards.

### P1-06 · Loyalty engine (pure services)
**Depends on:** P1-05.
**Read:** PRODUCT §5, §6, §10 (happy hour), §19; ENGINEERING §7–8.
**Build:** pure functions with explicit inputs and `now`:
- `calculateAward({ program, amountPence, requestedAt, multipliers, streakState })` → points (per-visit or floor(pence/100 × rate)), applied multiplier, streak bonus.
- `applyAward(state, award, program)` → new balance, ingots completed (can be > 1), overflow carried, milestones crossed (each only once per ingot cycle), tier, streak state.
- `estimateVisitsToNext(state, history)`; `computeExpiry(entries, program, now)`.
- Types: `Points`, `Pence` branded.
**Acceptance criteria:** deterministic; no I/O; property tests prove balance never negative, gold is conserved across overflow, milestones never double-unlock.
**Edge cases:** award exactly fills the ingot; award fills two ingots; zero-amount per-visit; rounding down for per-pound; streak boundary at UK midnight; tier threshold crossed by a multi-ingot award; programme version change between request and approval (engine uses the version active at `requestedAt`).
**Tests:** ≥ 30 unit cases + property-based tests (fast-check); coverage ≥ 95% for the module.
**Verify:** coverage report.

## Sub-phase P1-C · Requests, approvals, realtime

### P1-10 · Realtime (SSE) infrastructure
**Depends on:** P0-07.
**Read:** ARCHITECTURE §7; SECURITY §3.
**Build:** `/api/sse/me` and `/api/sse/shop/[shopId]` (authn + authz, origin check), heartbeat every 25s, Redis pub/sub channels `user:{id}` and `shop:{id}`, typed events (`request_created`, `request_decided`, `points_credited`, `reward_unlocked`, `redemption_confirmed`, `notification`), per-user connection cap; client hook with exponential backoff + jitter and full refetch on reconnect.
**Acceptance criteria:** staff of shop B cannot subscribe to shop A (403); events delivered across two app instances; reconnect refetches state; no memory leak after 1,000 connect/disconnect cycles (integration loop).
**Tests:** integration for authz, fan-out, cap; unit for client backoff.

### P1-11 · Points requests (customer)
**Depends on:** P1-09, P1-10.
**Read:** PRODUCT §5, §19; SECURITY §6; ENGINEERING §7.
**Build:**
- Migration: `point_requests` with status enum `pending | awaiting_owner | approved | rejected | expired`, partial unique index on one open request (`pending` or `awaiting_owner`) per membership, unique `idempotency_key`.
- `requestPoints(shopId, idempotencyKey)`: membership required; shop not suspended/closed; daily cap 5 per customer per shop (UK day); creates request; publishes `request_created`.
- Pending state on the shop page with live updates; offline queue (retries with the same key when back online).
- Jobs: expire requests after 24h (every 5 min) and notify the customer; remind the shop after 30 min pending (once).
**Acceptance criteria:** double tap → one request; two devices simultaneously → one open request; 6th request in a UK day → friendly limit; expiry and reminder fire once each.
**Tests:** integration with parallel calls; job tests with injected clock; authz entries.

### P1-12 · Approve / reject, owner approval, reversals, receipts
**Depends on:** P1-11, P1-06.
**Read:** PRODUCT §5, §11; ARCHITECTURE §4–5; ENGINEERING §7; SECURITY §12.
**Build:**
- Migrations: `ledger_entries` (append-only trigger), `rewards`, `receipts` (per-shop sequential number via counter row locked in the transaction).
- `approveRequest(requestId, { amountPence?, items?, receiptPhotoKey? })`: staff of that shop; compute points with the engine (programme version at `requested_at`, happy-hour multipliers hook); if points exceed the staff member's per-award limit → status `awaiting_owner` and notify owners; otherwise one transaction: lock request row, insert ledger entries (`earn`, `bonus_streak`), update membership counters (`purchase_count`, `last_visit_at`), unlock rewards/milestones, create receipt; after commit enqueue receipt PDF, push, SSE events; audit log.
- `ownerApprove(requestId)` for `awaiting_owner`; `rejectRequest(requestId, reason)` with preset reasons + free text.
- `reverseAward(receiptId, reason)` (owner): `reversal` entry, balance floored at zero, shortfall recorded and shown; rewards already redeemed are not clawed back (shown in shortfall note).
- Receipt PDF job (worker) using brand template; "Digital receipt" wording; VAT number only if set.
- Minimal approve UI in the dashboard (full requests page in P2).
**Acceptance criteria:** approving twice → CONFLICT; ledger cannot be updated/deleted; above-limit approval routes to owner; receipt numbers unique and gapless per shop under concurrency; reversal never makes a balance negative.
**Edge cases:** request expired between viewing and approving; customer left the shop meanwhile; programme changed between request and approval; staff deactivated mid-approval.
**Tests:** integration for every criterion and edge case (including concurrent approvals and receipt numbering); authz entries; E2E journey 2.
**Verify:** test output; DB inspection of ledger and receipts.

### P1-13 · Points expiry job
**Depends on:** P1-12.

**Acceptance criteria:** idempotent; never expires more than the balance; respects programme versions.
**Tests:** job tests with injected clock across month ends and DST.

### P1-17 · Data-integrity reconciliation
**Depends on:** P1-12, P1-16.
**Read:** TESTING §10; ARCHITECTURE §4, §6.
**Build:** nightly job (UK 04:00) and on-demand admin trigger that checks: per membership, ledger sum = cached balance (if any cached fields exist) and ≥ 0; receipt numbers gapless and unique per shop; no reward redeemed twice; no request approved twice; every `approved` request has ledger entries. Mismatches recorded in an `integrity_issues` table, sent to Sentry, shown on the admin System page (P2).
**Acceptance criteria:** clean on seed data; deliberately corrupted test data produces the expected issues; job is read-only (never "fixes" data automatically).
**Tests:** integration tests per check (clean and corrupted cases).

## P1 definition of done
- Engine coverage ≥ 95% and mutation score ≥ 80%; DB constraints proven by concurrency tests; ledger append-only verified; reconciliation clean on staging; k6 smoke within targets.
- Signature moments verified on WebKit and Chromium with skill reviews passed.
- Reviewer passes (code, security, design) recorded; HUMAN_TASKS updated for P2 (R2, Turnstile, email domain).
