# P5 — Completeness, hardening, PWA, Play Store, release candidate

**Goal:** turn a feature-complete app into a launch-ready product: every customer screen complete, installable app on Android (Play) and iPhone (Home Screen), all legal pages, every security item closed, performance and accessibility verified, load-tested, production infrastructure with backups and monitoring, and a rehearsed release.

## How to work this phase
- **Self-verification is part of every task:** test first for logic, run the app, inspect screenshots, try to break it (TESTING §7–8). **Close every sub-phase with `/subphase-complete`** (full regression, exploratory QA, reviews, push, CI + staging verification) and the phase with `/phase-complete`.
- Sub-phases A → D. Read CLAUDE.md, ENGINEERING §1, §11–12, SECURITY §13, TESTING §4–5, and each task's **Read** list.
- This phase is about evidence: every gate produces a saved report in `.artifacts/` (git-ignored) and a summary line in SESSION_LOG.md.
- End each sub-phase with the relevant reviewers, update PROGRESS + HUMAN_TASKS, commit, push.

## Sub-phase P5-A · Customer completeness and installable app

### P5-01 · Me, privacy and data, help
**Depends on:** P4 complete.
**Read:** PRODUCT §17; DESIGN §15 screen 12; reference `m12`/`d12`; COMPLIANCE §2.
**Build:** Me (screen 12): profile header, member card, stats, monthly recap card, menu (receipts with PDF download, saved offers, my listings, refer a friend, notifications, install app, privacy and data, help and policies), toggles (sounds, reduce animations), active sessions with sign-out everywhere; edit profile (name, phone, birthday, per-shop marketing consents); self-service data export (job → email link, expiring) and account deletion (confirm unredeemed rewards are lost; 30-day completion; immediate sign-out; uses P2-13 deletion routine); help page with FAQs.
**Acceptance criteria:** export contains all the user's data across tables (test compares to a schema-driven list); deletion complete per P2-13 tests; desktop layout per screen 12.
**Tests:** integration for export completeness; E2E journey 12.

### P5-02 · PWA: manifest, service worker, offline, updates
**Depends on:** P1-14.
**Read:** PRODUCT §18; DESIGN §11.
**Build:** manifest (name, short name, theme/background colours from tokens, `display: standalone`, start URL `/wallet`, scope, maskable icons 192/512, Apple touch icon, screenshots); service worker (Serwist or equivalent): precache app shell and fonts, runtime cache for images (stale-while-revalidate, capped), network-first for HTML, offline fallback page, offline wallet snapshot and member card; update flow ("A new version is ready — refresh") without breaking an in-progress action; no caching of authenticated API responses beyond the explicit snapshots.
**Acceptance criteria:** Lighthouse PWA installability passes; app usable offline for wallet snapshot + member card; signing out clears cached personal data.
**Tests:** Playwright offline tests (Chromium); unit for cache rules.

### P5-03 · Install flows
**Depends on:** P5-02.
**Read:** PRODUCT §18; DESIGN §11.
**Build:** install chip on every customer screen until installed; Android/desktop Chrome uses `beforeinstallprompt`; iOS Safari shows an animated guide sheet (Share → Add to Home Screen → Open as Web App on); hidden in standalone mode and inside the Android TWA; dismissal remembered for 14 days.
**Acceptance criteria:** correct behaviour on Chromium, WebKit (iOS emulation) and standalone mode; no prompt shown inside the TWA.
**Tests:** E2E journey 13.

### P5-04 · Android app (Trusted Web Activity) and Play listing
**Depends on:** P5-02; HUMAN_TASKS Play Console account, production domain.
**Read:** PRODUCT §18; ARCHITECTURE §1 (Android row).
**Build:** Bubblewrap project in `twa/` (package id, app name, icons, splash, theme colours, notification delegation), signing key creation instructions in HUMAN_TASKS (keystore never committed), Digital Asset Links at `/.well-known/assetlinks.json` per environment; Play listing assets in `twa/listing/` (icon 512, feature graphic 1024×500, phone screenshots, short and full descriptions, privacy policy URL, data safety answers draft); internal testing track build instructions.
**Acceptance criteria:** TWA opens full-screen without browser UI (asset links verified); push notifications work in the TWA; data safety draft matches actual data collection.
**Verify:** human installs internal test build on a real Android phone (HUMAN_TASKS).

## Sub-phase P5-C · Quality gates

### P5-07 · Security checklist completion
**Depends on:** P5-06.
**Read:** SECURITY (all), especially §13.
**Build:** tick every SECURITY item with evidence or a DECISIONS entry; decide on Postgres RLS (implement for shop-scoped tables if it fits pooling, otherwise document why app-layer authz + tests suffice); rotate all staging-derived secrets for production; verify headers grade (securityheaders.com A or better); ZAP baseline + authenticated scan on staging; Semgrep/CodeQL/OSV clean of high/critical; SBOM generated; recommend independent penetration test and Cyber Essentials Plus (HUMAN_TASKS for the client).
**Acceptance criteria:** zero unresolved high/critical findings; authz coverage 100%.

### P5-08 · Performance pass
**Depends on:** P5-02.
**Read:** DESIGN §12; ENGINEERING §11; CLAUDE.md §3 (judgment rule).
**Build:** `robots.txt` (production allows `/`, `/s/*`, `/offers`, `/join`, `/legal/*`; disallows app, dashboard, admin, API; staging disallows all) and `sitemap.xml` for public pages; Lighthouse CI on all customer routes and key dashboard routes; bundle analysis per route; image audit (sizes, formats, `sizes` attributes); DB query review on seeded scale (EXPLAIN for top 20 queries by frequency); caching headers review; fix regressions; log accepted overruns.
**Acceptance criteria:** budgets met or within the judgment rule with DECISIONS entries; no route ships an unused heavy dependency.

### P5-09 · Accessibility pass
**Depends on:** P5-01.
**Read:** DESIGN §13; ENGINEERING §12.
**Build:** axe on every route (customer, shop, admin) at mobile and desktop; keyboard-only walkthrough of the critical journeys; screen-reader spot checks (VoiceOver on iOS Safari emulation notes + NVDA/ChromeVox where possible) for points credited, rewards, forms; fix findings.
**Acceptance criteria:** zero serious/critical axe violations; critical journeys completable by keyboard; live regions announce points and rewards.

### P5-10 · Visual regression baselines
**Depends on:** P5-01.
**Read:** DESIGN §15; TESTING §1.
**Build:** Playwright screenshot tests for all 20 key screens × (mobile WebKit, mobile Chromium, desktop) with seeded deterministic data and animations disabled; compare with `design/reference/` images in a `design-reviewer` pass and fix meaningful deviations.
**Acceptance criteria:** baselines committed; diff threshold 0.2%; design review findings resolved or logged.

### P5-11 · Load test and cross-device verification
**Depends on:** P5-08.
**Read:** TESTING §5.
**Build:** k6 scenarios per TESTING §5 against staging (sized like production); monitor DB, Redis, queue lag, error rate; fix bottlenecks and re-run; real-device checklist in HUMAN_TASKS (Android mid-range phone, iPhone Safari, iPhone installed PWA, desktop Chrome/Safari/Edge).
**Acceptance criteria:** p95 < 300ms for actions, < 800ms server time for pages, error rate < 0.5%, no queue backlog > 60s; human device checklist completed.

## Sub-phase P5-D · Production readiness

### P5-12 · Production infrastructure, backups, monitoring
**Depends on:** P5-07; HUMAN_TASKS production VPS, database, DNS.
**Read:** ARCHITECTURE §9–12; SECURITY §11.
**Build:** production compose (web ×2+, worker, redis, caddy), Cloudflare (proxy, WAF managed rules, cache rules for public pages and CDN origin), production secrets, email domain authentication (SPF, DKIM, DMARC) verified with a deliverability test, database PITR confirmed plus nightly encrypted logical dump to R2, monthly restore drill script (run once now on staging), uptime monitors (web, health, worker heartbeat), **synthetic monitoring** (TESTING §10: scheduled Playwright checks every 10 minutes against production for landing, sign-in, wallet with a test account, offers feed, dashboard login), post-deploy production smoke, nightly reconciliation alerts, alerting (error spike, failed logins spike, fraud high severity, queue backlog, backup failure, synthetic check failure), admin System page shows last backup.
**Acceptance criteria:** restore drill completed with timing recorded; alerts fire in a test; production health green behind maintenance page.

### P5-13 · Runbook, operator docs, release workflow
**Depends on:** P5-12.
**Read:** SECURITY §12; ARCHITECTURE §9.
**Build:** `docs/RUNBOOK.md` (deploy, rollback, restore, rotate secrets, incident triage and comms, ICO 72-hour process, common failures); `docs/ADMIN_GUIDE.md` for the platform team; `docs/SHOP_GUIDE.md` for shop owners (plain English); release workflow (tag → GitHub environment approval → deploy → smoke → done) rehearsed with a dry run to production behind the maintenance page.
**Acceptance criteria:** dry run completes and is rolled back successfully; docs reviewed by the `code-reviewer` subagent for accuracy against the code.

### P5-14 · Release candidate
**Depends on:** all P5 tasks.
**Build:** full gate run (TESTING §4 pre-production list, including journeys 1–16 with unhappy paths on all projects, full k6 load test, authenticated ZAP, mutation testing on all rules modules, live provider smoke, reconciliation clean, restore drill), all reports saved, `progress/RELEASE_CANDIDATE.md` summarising gates, known issues, deferred items and client actions; demo notes via `/demo`.
