# P5 — Completeness, hardening, PWA, Play Store, release candidate

**Goal:** turn a feature-complete app into a launch-ready product: every customer screen complete, installable app on Android (Play) and iPhone (Home Screen), all legal pages, every security item closed, performance and accessibility verified, load-tested, production infrastructure with backups and monitoring, and a rehearsed release.

## How to work this phase
- **Before the first task of this phase**, run a brief review: fill any missing Edge cases and measurable Acceptance criteria in this file (one agent, cheap; commit with the first task).
- **Self-verification is part of every task:** test first for logic, run the app, inspect screenshots, try to break it (TESTING §7–8).
- **Task:** `pnpm gate:task` only (check + test:int + build + the task's E2E specs on the production build, Chromium + WebKit). No full regression, no exploratory QA agent, no all-project runs. Tasks touching auth, authz, sessions, rate limits, payments, uploads, crypto or PII run `security-reviewer` on the task diff before the tick.
- **Sub-phase close (`/subphase-complete`) is light:** CI green on the last commit (CI already ran the full suite; do not re-run it locally); staging deploy + smoke + Sentry check; `code-reviewer` (+ `security-reviewer` for server/auth code, `design-reviewer` for UI) on commits not already reviewed at task tick; exploratory QA only if the sub-phase added or changed screens, scoped to those screens at 320/390/1440 on Chromium + WebKit; update PROGRESS + HUMAN_TASKS; push.
- **Phase close is the one heavy gate:** P5-14 runs `pnpm gate:phase` once + definition of done + demo; `/phase-complete` does not repeat it. Demo for P5: recorded dry run (video) of the Demo 6 script.
- Sub-phases A → D. Read CLAUDE.md, ENGINEERING §1, §11–12, SECURITY §13, TESTING §4–5, and each task's **Read** list.
- This phase is about evidence: every gate produces a saved report in `.artifacts/` (git-ignored) and a summary line in SESSION_LOG.md.
- Order in P5-D: P5-12 (production infrastructure) → P5-11 (load test on it) → P5-13 → P5-14.

### P5-02 · PWA: manifest, service worker, offline, updates
**Depends on:** P1-14.
**Read:** PRODUCT §18; DESIGN §11.
**Build:** extends the manifest and service worker skeleton from P1-14 (no second worker; P3-07's push handler kept): manifest completed (name, short name, theme/background colours from tokens, `display: standalone`, start URL `/wallet`, scope, maskable icons 192/512, Apple touch icon, screenshots); service worker: precache app shell and fonts, runtime cache for images (stale-while-revalidate, capped), network-first for HTML, offline fallback page, offline wallet snapshot and member card; no caching of authenticated API responses beyond the explicit snapshots. Platform behaviour per PRODUCT §18:
- Offline member QR: the cached token keeps its normal 5-min lifetime; offline, the QR shows only while it is unexpired, then the card shows the member ID large with "Offline — ask staff to type your member ID".
- Update prompt: a new version waits and shows a non-blocking "Update available" toast, applied only on tap; never shown and never reloads while a redeem code, a pending request, a celebration, the staff approve panel or the member-QR scanner is open.
- Notification permission only after the "Turn on notifications" pre-prompt, never on first launch; on Android 13+ the TWA requests `POST_NOTIFICATIONS` at that moment; if denied, settings explain how to enable it and the inbox still works.
- iOS storage eviction: every cache is optional (empty cache → normal online load, never an error); the push subscription is re-checked on each open and re-created if permission is still granted.
- TWA fallback (web side; packaging in P5-04): Custom Tabs, then WebView; sign-in, wallet, requests and member QR work in both; in a WebView the Google button is hidden (magic link offered) and settings explain that push is unavailable and the inbox is used.
**Acceptance criteria:** Lighthouse PWA installability passes; app usable offline for wallet snapshot + member card; offline QR hidden once the cached token expires; update toast never appears or reloads while any of the listed flows is open; signing out clears cached personal data; cleared storage loads normally and re-creates the push subscription when permission is granted; an installed PWA from the P1-14 skeleton updates to this worker without losing its push subscription; WebView user agent shows no Google button.
**Tests:** Playwright offline tests (Chromium) incl. token expiry offline; update-prompt suppression per listed flow; cleared-storage reload; WebView UA simulation; unit for cache rules; upgrade test from the P1-14 worker.

## Sub-phase P5-D · Production readiness

Order: P5-12 → P5-11 → P5-13 → P5-14 (production infrastructure first, then the release load test on it, before go-live).

### P5-12 · Production infrastructure, backups, monitoring
**Depends on:** P5-07; HUMAN_TASKS managed hosts, managed Postgres, DNS, secrets manager, client budget confirmation (H-21).
**Read:** ARCHITECTURE §9–12; SECURITY §11.
**Build:**
- Topology as code (compose + provisioning scripts): Cloudflare (proxy, WAF managed rules, bot rules, cache rules for public pages and the `cdn.` origin, origin lock via Authenticated Origin Pulls or Tunnel so the origin is not reachable directly) → ≥ 2 app hosts in separate failure domains (web replicas, rolling deploys one replica at a time) → workers on separate host(s) → managed Postgres (London/EU) with HA standby, PITR and PgBouncer (transaction mode) → Redis split: `redis-queue` (BullMQ + rate limits; AOF everysec, `noeviction`, replica) and `redis-cache` (cache + pub/sub; `allkeys-lru`). R2 with versioning and cross-bucket replication for uploads and receipts. Connection budget (replicas × pool + workers ≤ 80% of `max_connections`) checked.
- Production secrets in a secrets manager or GitHub Environments, never on disk outside root-only files.
- Email domain authentication (SPF, DKIM, DMARC) verified with a deliverability test; paid tiers for email, Sentry/observability and DB; budget and quota alerts at 70%.
- Backups: PITR confirmed plus nightly encrypted logical dump to R2 (35-day retention); restore drill script; admin System page shows last backup.
- Monitoring: uptime monitors (web, `/api/health/live`, worker heartbeat), **synthetic monitoring** (TESTING §10: scheduled Playwright checks every 10 minutes against production for landing, sign-in, wallet with a test account, offers feed, dashboard login), post-deploy production smoke, nightly reconciliation alerts, alerting to the on-call channel (error spike, failed logins spike, fraud high severity, queue backlog, outbox age, backup failure, synthetic check failure, SLO burn).
- Cost model per 1,000 shops (hosting, DB, Redis, R2, email, observability, AI) written into ARCHITECTURE and shared with the client.
**Acceptance criteria:**
1. Restore drill in an isolated DR environment (not production) from PITR: RPO ≤ 5 min (DB) and ≤ 1 min (queue Redis), RTO ≤ 1 h, timings recorded in RUNBOOK.
2. Failover under load: with k6 at forecast peak, killing one app host and failing over Postgres and the `redis-queue` primary keeps errors < 1% during failover with no lost jobs (outbox and queue counts reconciled).
3. Every alert above fires in a test and reaches the on-call channel.
4. Origin refuses direct (non-Cloudflare) requests; R2 versioning and replication verified by restoring a deleted object.
5. Host rebuild from the provisioning scripts rehearsed and timed.
6. Production health green behind the maintenance page.

### P5-11 · Load test and cross-device verification
**Depends on:** P5-12 (runs on the production-shaped environment before go-live), P5-08.
**Read:** TESTING §5.
**Build:** k6 scenarios per TESTING §5 against the production-shaped environment (production behind the maintenance page, or an identical copy), dataset seeded at the 12-month forecast volume (capacity model: 2,000 shops, 500,000 members); profiles: 2× forecast peak (600 req/s) for 30 min; 2 h soak at peak (300 req/s); 5× spike; failover (kill one app host and the Redis primary during load); 20,000 concurrent SSE connections; one announcement fanned out to 100,000 members; 50 scans/s on one shop. Monitor DB, Redis, queue lag, outbox age, error rate; fix bottlenecks and re-run; seeded data removed afterwards. Real-device checklist in HUMAN_TASKS (Android mid-range phone, iPhone Safari, iPhone installed PWA, desktop Chrome/Safari/Edge; VoiceOver and TalkBack passes).
**Acceptance criteria:** actions p95 < 300 ms, p99 < 800 ms; page server time p95 < 800 ms; errors < 0.5% (< 1% during failover, no lost jobs); queue lag < 60 s; SSE delivery p95 < 3 s; announcement fan-out to 100,000 members < 10 min; no memory growth over the 2 h soak; human device checklist completed. Reports in `.artifacts/` and the capacity model updated.

## P5 definition of done
- All quality gates passed with saved reports; RC document written; production infrastructure meets RPO/RTO in a drill; release load test passed on the production-shaped environment; production rehearsed incl. rollback; on-call rota in place; pen test booked; HUMAN_TASKS lists only client-side or launch-day items.
