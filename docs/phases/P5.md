# P5 — Completeness, hardening, PWA, Play Store, release candidate

**Goal:** turn a feature-complete app into a launch-ready product: every customer screen complete, installable app on Android (Play) and iPhone (Home Screen), all legal pages, every security item closed, performance and accessibility verified, load-tested, production infrastructure with backups and monitoring, and a rehearsed release.

**Target date:** Tue 12 Jan 2027 (plan v5 re-baseline; assumptions in PHASES.md and PROGRESS). Production is the single Hostinger VPS on free tiers (ARCHITECTURE §1, §9–10; DECISIONS "Plan v5: single VPS, free tiers").

## How to work this phase
- **Before the first task of this phase**, run a brief review: fill any missing Edge cases and measurable Acceptance criteria in this file (one agent, cheap; commit with the first task).
- **Self-verification is part of every task:** test first for logic, run the app, inspect screenshots, try to break it (TESTING §7–8).
- **Task:** `pnpm gate:task` only (check + test:int + build + the task's E2E specs on the production build, Chromium + WebKit). No full regression, no exploratory QA agent, no all-project runs. Tasks on the security-relevant list (CLAUDE.md §4) run `security-reviewer` on the task diff before the tick.
- **Sub-phase close (`/subphase-complete`) is light:** CI green on the last commit (CI already ran the full suite; do not re-run it locally); staging deploy + smoke + Sentry check; `code-reviewer` (+ `security-reviewer` for server/auth code, `design-reviewer` for UI) on commits not already reviewed at task tick; exploratory QA only if the sub-phase added or changed screens, scoped to those screens at 320/390/1440 on Chromium + WebKit; update PROGRESS + HUMAN_TASKS; push.
- **Phase close is the one heavy gate:** P5-14 runs `pnpm gate:phase` once + definition of done + demo; `/phase-complete` does not repeat it. Demo for P5: recorded dry run (video) of the Demo 6 script.
- Sub-phases A → D. Read CLAUDE.md, ENGINEERING §1, §11–12, SECURITY §13, TESTING §4–5, and each task's **Read** list.
- This phase is about evidence: every gate produces a saved report in `.artifacts/` (git-ignored) and a summary line in SESSION_LOG.md.
- Order in P5-D: P5-12 (production infrastructure) → P5-11 (load test on it) → P5-13 → P5-14.

### P5-02 · PWA: manifest, service worker, offline, updates
**Depends on:** P1-14.
**Read:** PRODUCT §18; DESIGN §11.
**Build:** extends the manifest and service worker skeleton from P1-14 (no second worker; P3-07's push handler kept): manifest completed (name, short name, theme/background colours from tokens, `display: standalone`, start URL `/wallet`, scope, maskable icons 192/512, Apple touch icon, screenshots); service worker: precache app shell and fonts, runtime cache for images (stale-while-revalidate, capped), network-first for HTML, offline fallback page, offline wallet snapshot and member card; no caching of authenticated API responses beyond the explicit snapshots. Platform behaviour per PRODUCT §18:
- Offline member QR: the cached token keeps its normal 5-min lifetime; offline, the QR shows only while it is unexpired, then the card shows the member ID large with "Offline — ask staff to type your member ID".
- Update prompt: a new version waits and shows a non-blocking "Update available" toast, applied only on tap; never shown and never reloads while a redeem code, a pending request, a celebration, the staff approve panel or the member-QR scanner is open.
- Notification permission only after the "Turn on notifications" pre-prompt, never on first launch; on Android 13+ the TWA requests `POST_NOTIFICATIONS` at that moment; if denied, settings explain how to enable it and the inbox still works.
- iOS storage eviction: every cache is optional (empty cache → normal online load, never an error); the push subscription is re-checked on each open and re-created if permission is still granted.
- TWA fallback (web side; packaging in P5-04): Custom Tabs, then WebView; sign-in, wallet, requests and member QR work in both; in a WebView the Google button is hidden (magic link offered) and settings explain that push is unavailable and the inbox is used.
**Acceptance criteria:** Lighthouse PWA installability passes; app usable offline for wallet snapshot + member card; offline QR hidden once the cached token expires; update toast never appears or reloads while any of the listed flows is open; signing out clears cached personal data; cleared storage loads normally and re-creates the push subscription when permission is granted; an installed PWA from the P1-14 skeleton updates to this worker without losing its push subscription; WebView user agent shows no Google button.
**Tests:** Playwright offline tests (Chromium) incl. token expiry offline; update-prompt suppression per listed flow; cleared-storage reload; WebView UA simulation; unit for cache rules; upgrade test from the P1-14 worker.

### P5-12 · Production infrastructure, backups, monitoring
**Depends on:** P5-07; HUMAN_TASKS DNS on Cloudflare (H-07), UptimeRobot account with both phones, R2 backup bucket + scoped token (H-08), backup OpenPGP public key (H-26), client acceptance of launch-tier numbers and the single-host risk (H-21).
**Read:** ARCHITECTURE §1, §9–12; SECURITY §11; RUNBOOK (deploy, backup, restore).
**Build:** the production stack on the single Hostinger VPS per ARCHITECTURE §1/§9 — host hardening, the production Compose project (Caddy, 2 web replicas, worker + outbox relay, Postgres + PostGIS, `redis-queue`, `redis-cache`, Umami; memory limits), Cloudflare Tunnel, registry-free deploy (`docker save | zstd | ssh docker load`, last 3 images kept) and the backup jobs were provisioned in P0-15. This task makes production launch-ready; it adds no hosts or topology.
- Production secrets generated fresh and delivered by the deploy job from GitHub secrets (environment or repository secrets per the GitHub mode in CLAUDE.md §1) to root-only files on the host; the only other copy is the developers' password manager; Claude never sees them. No separate secrets manager.
- Cloudflare free rules: proxy on, free managed WAF rules, rate-limit rule backstops (`/s/*`, `/api/auth/*`; our Redis limits are the real control), cache rules for static assets and the `cdn.` origin only (HTML never cached), origin reachable only through the Tunnel (no inbound 80/443 on the host).
- Email domain authentication (SPF, DKIM, DMARC) for Resend and Brevo, verified with a deliverability test; the P2-11 email budget counter live in production.
- Quota alerts at 70% for every free tier, each tested: Resend/Brevo daily and monthly sends, Sentry errors (sample rates keep it under ~4,000/month), R2 storage (10 GB covers uploads + backups + the audit-log bucket) and operations, GitHub Actions credit, UptimeRobot monitor count, Gemini spend (app daily cap). Where a provider offers no alert, a scheduled health-job check does it.
- Backups verified in production: nightly `pg_dump -Fc` of the app and Umami databases, encrypted with the backup OpenPGP key (private key never on the VPS), uploaded to the R2 backup bucket with its bucket-scoped token, 35-day lifecycle rule; wal-g WAL archiving (archive_timeout 60 s, weekly base backup, retention that keeps the disk from filling); alerts: no successful dump in 26 h, WAL archive lag > 10 min, disk > 80%; the monthly automated restore drill scheduled, its last result on the admin System page. Hostinger's own weekly backups are an extra layer only, never relied on.
- Monitoring: UptimeRobot free (web, `/api/health/live`, worker heartbeat, staging) alerting both developers' emails and the app on both phones; the scheduled health job (queue depth/lag, outbox age, failed jobs, last backup and drill, disk, DB size, SSE connections) mailing both developers (critical mail); Sentry free (one owner, alert rules forwarding to both developers); synthetic checks (TESTING §10: landing, sign-in, wallet with a test account, offers feed, dashboard login every 10 min) run as a scheduled container on the host against the public URL through Cloudflare, not on GitHub Actions (10-minute runs would exhaust the minutes budget); post-deploy production smoke; nightly reconciliation alerts. Alerts: error spike, failed-logins spike, fraud high severity, queue backlog, outbox age, backup failure, WAL lag, disk, synthetic check failure, quota 70%, SLO burn.
- Rebuild-and-restore rehearsal, once before launch: a fresh VPS (temporary hourly VPS, or a local VM) built from the infra/ scripts, the latest dump restored and WAL replayed to a chosen point, outbox "replay since <timestamp>" run, smoke green.
- Cost note in ARCHITECTURE, shared with the client: Hostinger KVM 4 £9.99/month on the 24-month promo (£239.76 upfront), **renewal £24.99/month**; Cloudflare (DNS, CDN, Tunnel, Turnstile, R2 ≤ 10 GB), Resend, Brevo, Sentry, UptimeRobot, Umami (self-hosted) at £0; Gemini pay-as-you-go up to its cap; GitHub Pro (about $4/month; confirm at purchase) if option (a); domain renewal; what each free tier costs when exceeded (e.g. R2 per GB above 10 GB) and the scale-path triggers (ARCHITECTURE §12.1).
**Acceptance criteria:**
1. The rebuild-and-restore rehearsal meets RTO ≤ 2 h and RPO ≤ 5 min (24 h if WAL archiving was blocked, with its DECISIONS entry); the outbox replay re-dispatches without duplicate side effects; timings recorded in RUNBOOK.
2. Production backups proven: a dump and WAL segments present in R2, unreadable without the backup OpenPGP private key, restorable; the restore drill result shown on the System page.
3. Every alert above fires in a test and reaches both developers (email, and phone push for uptime).
4. Origin refuses direct requests (no inbound 80/443; reachable only through the Tunnel); HTML responses never cached at Cloudflare (`cf-cache-status` is never `HIT` on HTML).
5. Every free-tier quota has a tested 70% alert or a scheduled check.
6. Production health green behind the maintenance page; every production container within its memory limit with the headroom in infra/.

### P5-11 · Load test and cross-device verification
**Depends on:** P5-12 (runs on production before go-live), P5-08.
**Read:** TESTING §5; ARCHITECTURE §12.1.
**Build:** k6 scenarios per TESTING §5, run from a developer machine or a GitHub runner (counted against the minutes budget), against production behind the maintenance page before go-live; dataset seeded at the launch-tier volume (200 shops, 50,000 members), removed afterwards; staging stays running at its normal limits during the run (it shares the host, so production must cope with it present). Profiles: 2× launch peak (60 req/s) for 30 min; 1 h soak at peak (30 req/s); a short 5× spike (150 req/s, ~2 min); 1,000 concurrent SSE connections; one announcement fanned out to 10,000 members; 10 scans/s on one shop. Restart test during load: restart one web replica, the worker, `redis-queue` and Postgres in turn. Monitor host CPU/RAM/disk, DB, Redis, queue lag, outbox age, error rate; fix bottlenecks and re-run. Scale-tier numbers (ARCHITECTURE §12.1) are not tested; this run baselines their trigger metrics. Real-device checklist in HUMAN_TASKS (Android mid-range phone, iPhone Safari, iPhone installed PWA, desktop Chrome/Safari/Edge; VoiceOver and TalkBack passes).
**Acceptance criteria:** actions p95 < 300 ms, p99 < 800 ms; page server time p95 < 800 ms; errors < 0.5% outside restart windows; queue lag < 60 s; SSE delivery p95 < 3 s; announcement fan-out to 10,000 members < 10 min; no memory growth over the 1 h soak and no container OOM-killed; restart test: no lost jobs (outbox and queue counts reconciled), each service healthy again within the RUNBOOK recovery target (default ≤ 2 min, errors back under 0.5% within 5 min), SSE clients reconnect and refetch, a web-replica restart keeps errors < 1% (the other replica serves); human device checklist completed. Reports in `.artifacts/` and the capacity model updated.
