# P0 — Foundation and design system

**Goal:** a production-grade skeleton: secure auth for every role, an authorisation layer that makes cross-shop leaks structurally hard, background jobs, a complete design system with motion and sound foundations, the three portal shells, CI, and a staging environment the client can see. Every later phase builds on this; shortcuts here multiply.

## How to work this phase
- Work sub-phases in order (A → E). Inside a sub-phase, follow task order unless "Depends on" allows otherwise.
- Before each task: read CLAUDE.md, `docs/ENGINEERING.md` §1–5, and the task's **Read** list (only those sections).
- A task is ticked in `docs/PHASES.md` only when every **Acceptance criterion** has evidence from this session (ENGINEERING §1). Record the evidence summary in SESSION_LOG.md.
- At the end of each **sub-phase**: run the `code-reviewer` subagent on the sub-phase diff, fix high findings, update PROGRESS.md + HUMAN_TASKS.md, commit and **push** (two developers relay; see CLAUDE.md §1).

### P0-03 · Database foundation
**Depends on:** P0-02.
**Read:** ARCHITECTURE §4; ENGINEERING §6–7.
**Build:**
- Drizzle client with pooling; separate migration connection; scripts `db:generate`, `db:migrate`, `db:seed`, `db:reset` (refuses to run unless `APP_ENV=local`).
- Helpers: UUIDv7 generator, `timestamps()` columns, `updated_at` trigger.
- First migration: auth library tables; `customer_profiles`; `shops` (core columns incl. PostGIS `location geography(Point,4326)`, status enum); `shop_staff`; `memberships` (unique `(user_id, shop_id)`); `audit_logs`; `feature_flags`; `content_settings`.
- Generic `reject_mutation()` trigger function; attached to `audit_logs` (later `ledger_entries`).
- `src/server/repos/_base.ts`: helpers that require a scope parameter; a lint or type-level pattern that makes unscoped access awkward.
- `src/lib/codes.ts`: crypto-random Crockford base32 (alphabet excludes 0, O, 1, I, L), configurable length/format, collision retry on unique violation (max 5 attempts, then error).
**Acceptance criteria:**
- Migrations apply to an empty DB; re-running is a no-op.
- `UPDATE`/`DELETE` on `audit_logs` raises an error at DB level.
- Code generator only emits allowed characters, correct length, retries on unique violation.
**Edge cases:** PostGIS extension missing → migration fails with clear message; migration run against non-empty DB stays expand-only.
**Tests:** integration (append-only trigger, unique constraints); unit (code generator alphabet/length/retry, distribution sanity over 10k samples).
**Verify:** test output; `\d audit_logs` shows the trigger.

## Sub-phase P0-B · Security baseline, auth, authorisation

### P0-05 · Security baseline
**Depends on:** P0-02.
**Read:** SECURITY §5–6, §12; ENGINEERING §13.
**Build:**
- Middleware: per-request CSP nonce; headers exactly as SECURITY §5; `/dev/*` returns 404 when `APP_ENV=production`; request ID generation/propagation (`x-request-id`).
- Redis sliding-window limiter: `limit({key, max, windowSec})` → `{ok, remaining, resetAt}`; helpers for per-IP (respecting Cloudflare `CF-Connecting-IP` only when behind Cloudflare) and per-user keys; standard 429 handling for actions and routes.
- `assertSameOrigin(request)` for mutating route handlers.
- Turnstile client component + `verifyTurnstile(token, ip)` server helper (bypass key only in local/test).
- `pino` logger with redaction paths (tokens, cookies, authorization, email, phone, codes) and child loggers per request.
- `audit({actor, action, entity, entityId, meta})` writer.
**Acceptance criteria:**
- `curl -I` on `/` shows every header from SECURITY §5 with correct values.
- Inline `<script>` without nonce is blocked (manual console check documented).
- Limiter blocks at threshold and recovers after the window; IP extraction can't be spoofed via `X-Forwarded-For` outside trusted proxy.
- Logging an object containing an email and a token outputs them redacted.
**Tests:** limiter integration (real Redis), redaction unit test, header snapshot test, origin check unit test.
**Verify:** curl output; test output.

### P0-06 · Authentication for all roles
**Depends on:** P0-03, P0-05.
**Read:** PRODUCT §2–3; SECURITY §2, §5; DESIGN §15 screen 2; reference `m02`/`d02`.
**Build:**
- Better Auth with Drizzle adapter (fall back to Auth.js only if a required capability is missing; log decision).
- Customers: Google OAuth (state + PKCE; scopes `openid email profile`; reject unverified emails) and email magic link (single-use, 15 min, hashed token storage). No passwords for customers.
- Staff/admin: email + password (Argon2id; min 12 chars; breached-password check via k-anonymity range API with timeout and fail-open-with-warning), mandatory TOTP enrolment before any dashboard access, 10 hashed single-use recovery codes, optional passkeys if the library supports them cleanly.
- Account linking rule: one user per verified email; Google and magic link resolve to the same user. Document in DECISIONS.md.
- Sessions: `__Host-` cookies, `Secure`, `HttpOnly`, `SameSite=Lax`; idle timeouts customer 30d / staff 12h / admin 2h; rotation on sign-in and privilege change; session list + "sign out everywhere".
- Return-URL allowlist (internal paths only, normalised); everything else falls back to the role's home.
- Throttling: magic-link requests and staff/admin logins per SECURITY §6; lockout notification email after repeated failures.
- UI: customer sign-in (screen 2: shop context when coming from a shop), "check your inbox", expired/used link page; staff/admin sign-in, TOTP enrolment (QR + manual key), TOTP challenge, recovery code entry. Magic-link email via React Email (rendered through Mailpit locally).
- Role context: users who are both customer and staff get an explicit switcher; default portal per role.
**Acceptance criteria:**
- Google and magic-link sign-in both work; reused or expired links show the friendly page.
- No staff/admin route reachable before TOTP is enrolled and verified (tested per route group).
- `?return=https://evil.com`, `//evil.com`, `/\evil.com` all fall back safely.
- Known vs unknown email for magic link: identical response body and status.
- Session timeouts enforced per role (tested with injected clock).
**Edge cases:** unverified Google email; email casing differences; user deleted mid-session; TOTP clock drift (±1 step); recovery code reuse.
**Tests:** integration for link lifecycle, TOTP gate, recovery codes, return-URL validation, throttling, timeouts; E2E customer magic-link sign-in via Mailpit API on Chromium + WebKit.
**Verify:** E2E summary; screenshots of sign-in (mobile + desktop).

### P0-07 · Authorisation layer, action template, error model
**Depends on:** P0-06.

**Build:**

**Acceptance criteria:**
- A sample action demonstrates every template step.
- Matrix runner executes all role cases.
- Coverage script fails when an action is added without a matrix entry, and passes once added (demonstrate).
**Tests:** unit tests for policy functions; matrix self-test.
**Verify:** runner output; coverage script fail → pass demonstration.
