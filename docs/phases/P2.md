# P2 — Shop dashboard, onboarding and admin core

**Goal:** shops can apply, be activated (with manual payment), and run their day-to-day operations; the platform team can manage shops, customers, plans and data requests safely. This phase proves multi-tenant isolation across every dashboard and admin action.

**Target date:** Thu 10 Dec 2026 (plan v5 re-baseline; assumptions in PHASES.md and PROGRESS).

## How to work this phase
- **Before the first task of this phase**, run a brief review: fill any missing Edge cases and measurable Acceptance criteria in this file (one agent, cheap; commit with the first task).
- **Self-verification is part of every task:** test first for logic, run the app, inspect screenshots, try to break it (TESTING §7–8).
- **Task:** `pnpm gate:task` only (check + test:int + build + the task's E2E specs on the production build, Chromium + WebKit). No full regression, no exploratory QA agent, no all-project runs. Tasks touching auth, authz, sessions, rate limits, payments, uploads, crypto or PII run `security-reviewer` on the task diff before the tick. Every new action gets authz matrix entries in the same task.
- **Sub-phase close (`/subphase-complete`) is light:** CI green on the last commit (CI already ran the full suite; do not re-run it locally); staging deploy + smoke + Sentry check; `code-reviewer` (+ `security-reviewer` for server/auth code, `design-reviewer` for UI) on commits not already reviewed at task tick; exploratory QA only if the sub-phase added or changed screens, scoped to those screens at 320/390/1440 on Chromium + WebKit; update PROGRESS + HUMAN_TASKS; push.
- **Phase close is the one heavy gate:** `pnpm gate:phase` + definition of done + demo. P2-16 IS that run; `/phase-complete` does not repeat it. Demo for P2: recorded dry run on staging (video) of the Demo 3 script.
- Sub-phases A → C. Read CLAUDE.md, ENGINEERING §1, §4–6, §9–10, SECURITY §3, and each task's **Read** list.

### P2-02 · Requests page and member QR scanning
**Depends on:** P2-01.
**Read:** PRODUCT §5, §14 (Requests); DESIGN §8.7, §15 screen 18; reference `m18`/`d18`; SECURITY §6.
**Build:**
- Tabs: Pending (incl. awaiting owner), Approved today, Expired; cursor pagination.
- Approve side panel (desktop) / sheet with large number pad (mobile): amount, item quick-picks (owner-configurable list in settings), live gold preview from the engine (incl. multipliers), receipt photo (P2-05 pipeline), reject reasons.
- Scanner: `BarcodeDetector` where available, otherwise a lazy-loaded decoder; camera permission explainer; torch toggle where supported; manual member-ID entry fallback; verifies the signed token (P1-14) and opens the award panel for that member (creates an already-approved request for audit).
- New request: row slides in with highlight; `tick` sound when the tab is focused and sounds are on.
**Acceptance criteria:** forged/expired token → clear error; scan award recorded as a request with `source=scan`; per-award limit enforced; full keyboard operation on desktop; two staff approving the same request → one succeeds, the other sees "already approved".
**Edge cases:** camera denied; poor light; member not yet joined to this shop (offer to join them? — no: show "ask the customer to scan the shop QR first"); offline counter (queue disabled with clear message).
**Tests:** integration for scan award and concurrency; E2E journey 4 with a mocked camera stream.
**Verify:** screenshots m/d; test output.

### P2-05 · Shop settings and hardened upload pipeline
**Depends on:** P2-01; HUMAN_TASKS R2 credentials.
**Read:** PRODUCT §14 (Settings); ARCHITECTURE §8; SECURITY §8.
**Build:**
- Settings: profile, category, description, logo/cover/gallery (≤ 6) with cropper, hours editor (overnight support), closures calendar, location via postcode lookup (postcodes.io with timeout + cache) and adjustable map pin, Google Place ID (format validation + helper link), VAT number (format validation), item quick-picks, notification preferences, weekly email toggle, plan status (read-only).
- Upload pipeline (the hardened pipeline every later upload uses): `/api/uploads` issues presigned PUT (exact type + max size) to `incoming/`; `images` job verifies magic bytes, pixel and frame limits (animated images rejected), decodes, converts HEIC, re-encodes AVIF + WebP at needed sizes, strips all metadata incl. EXIF/GPS, writes to the public path, updates DB, deletes original; orphaned `incoming/` and replaced-image cleanup job.
- Separate `cdn.` origin serving only processed images with the correct `Content-Type`, `X-Content-Type-Options: nosniff`, never HTML or SVG.
**Acceptance criteria:** fixture suite rejected or sanitised as expected: polyglot file, SVG, animated GIF/WebP, 20k×20k PNG (decompression bomb), truncated file, wrong extension, zero-byte, oversized; output has no EXIF/GPS (test reads metadata); replaced and orphaned uploads cleaned up; every CDN response has `nosniff` and an image `Content-Type`, and nothing served from the CDN can execute script.
**Tests:** worker fixture tests (JPEG with GPS EXIF, PNG, HEIC, polyglot, SVG, animated GIF/WebP, fake extension, 20k×20k, truncated, zero-byte); header check on CDN responses; orphan cleanup job test.

### P2-09 · Applications, activation, payments, invoices
**Depends on:** P2-08.
**Read:** PRODUCT §15–16; DESIGN §15 screen 20; reference `m20`/`d20`; ARCHITECTURE §4 (applications, plans, payments, invoices).
**Build:** admin Applications list + detail (screen 20) with notes; reject with reason (email); activation in one transaction: record payment (amount, method, reference, paid date), plan (monthly/lifetime, start, expiry), create shop (code, QR, NFC tag record), owner invite, default loyalty programme from chosen template, invoice row with sequential number, outbox rows for the invoice PDF and emails; audit log. "Plans & payments" page: list, filter, record renewal payment (extends expiry), download invoices.
- Invoice legal fields: supplier name, address and company number (platform settings), customer (shop legal name and address), unique sequential invoice number, issue date and supply date, description, amount; VAT number, rate and VAT amount only when the platform is VAT-registered (setting), otherwise no VAT lines.
**Acceptance criteria:** activation is all-or-nothing (forced failure mid-way leaves no partial records and no emails); invoice numbers unique and sequential under concurrency; every invoice PDF contains the legal fields above (test parses the PDF text) and shows VAT lines only when registered; only Admin Owner/Finance can record payments.
**Tests:** integration for atomicity and numbering; invoice PDF field test (VAT registered and not); authz; E2E journey 10.

### P2-10 · Plan state machine and restricted mode
**Depends on:** P2-09.
**Read:** PRODUCT §15 (plan states); ENGINEERING §8.
**Build:** pure state machine (`pending → active → expiring (≤14 days) → grace (7 days) → restricted`; `suspended` and `closed` by admin; lifetime never expires); daily job 07:00 UK applying transitions and sending reminders at 14/7/1 days (each once); dashboard banners; `assertPlanAllows(action)` used by offers, announcements, featured requests (blocked when restricted) while approvals and redemptions remain allowed.
**Acceptance criteria:** transitions at exact UK day boundaries incl. DST; reminders deduplicated; every restricted action has a test proving it's blocked server-side.
**Tests:** unit for all transitions; job tests with injected clock; E2E journey 11.

### P2-11 · Email templates
**Depends on:** P0-06. Build first in P2-B (P2-08 to P2-10 send these).
**Read:** DESIGN §14; COMPLIANCE §3.
**Build:** this task owns every email template; other tasks consume them and never define ad-hoc email HTML (P0-06's magic-link email and P1's interim emails are replaced here; P3-07 consumes). React Email templates with plain-text versions, limited to the email budget (ARCHITECTURE §10): magic link, staff invite, application received / approved / rejected, activation (owner invite), invoice, plan reminders, data-request mails (data export ready, deletion confirmation), account recovery, lockout notice; the weekly owner email is added by P3-12. Customer loyalty events (request expired, points expiry warnings, reversal, programme change, shop closing) are in-app (+ push from P3-07) only and get no email template. Announcements, offers and marketing are never sent by email. A template registry marks each one `transactional` or `marketing` and gives its budget class; marketing emails (none at launch) would include one-click unsubscribe (`List-Unsubscribe` + `List-Unsubscribe-Post`). New templates added in later phases go into this registry and must fit the budget.
- Email budget enforcement (this task owns it unless P0 already delivered it): Resend free (100/day, 3,000/month) primary, Brevo free (300/day) failover behind the provider interface; daily send counter in `redis-queue` (not cache); alert at 70% of the combined daily cap (≈ 280/day); near the cap, drop in this order: weekly owner email → plan reminders → data-request notices queued to the next day (never dropped; legal deadline is a month) → invites and shop-account mail (application outcome, activation, invoice) queued to the next day → auth/security mail and ops alerts never dropped.
**Acceptance criteria:** render snapshot tests for every template; links use the correct environment URL; no PII beyond what's necessary; no email HTML exists outside the registry (static check); no template exists for an event outside the email budget (registry test); primary provider failure → the same mail goes via the secondary (integration with both providers mocked); at the cap the drop order above holds exactly (injected counter), and auth/security mail is never dropped by the budget logic (sent past 70% and at the cap).

## Sub-phase P2-C · Admin core

### P2-12 · Admin shops: list, detail, suspend, close, view-as-shop
**Depends on:** P2-09.
**Read:** PRODUCT §16, §19 (shop closes); SECURITY §3, §12.
**Build:** shops list with filters (status, plan, region, category) and search; detail (profile, plan, payments, staff, KPIs); suspend/restore with reason (emails owner); close shop: members notified in-app (+ push from P3), rewards honoured 30 days (redemptions still allowed), then archived by job; view-as-shop: read-only session (30 min), persistent banner, every page view audit-logged.
**Acceptance criteria:** view-as-shop cannot mutate (test calls every shop action under view-as context → all FORBIDDEN); closure timeline enforced by job.
**Tests:** integration for read-only enforcement and closure lifecycle.

### P2-13 · Admin customers: lookup, recovery, data requests, retention, blocking
**Depends on:** P2-12.
**Read:** PRODUCT §16, §17, §19 (lost access); SECURITY §7; COMPLIANCE §2.
**Build:**
- Lookup by name, email, phone (blind index), member ID; block/unblock account.
- Account recovery for lost Google/email access (PRODUCT §16): the customer proves member ID + last shop visited + phone; one admin opens the request, a second, different admin approves; then a 72h hold with a notice and cancel link sent to the old email; after the hold the login email changes with notification to old and new address; every step audited.
- Data export (DSAR, JSON + CSV via job) covering: profile, memberships, ledger, requests, redemptions, claims, feedback, listings, reveal logs, notifications, consents, devices, fraud flags (where lawful), notes about the customer. Tables added in later phases join the export's schema-driven list.
- Deletion requests with due dates (1 month) and status. Erasure (PRODUCT §17) anonymises the user and customer profile: name, email, phone ciphertext and blind index, birthday and birth year removed; the ledger and audit rows stay untouched and pseudonymous (they hold only membership/subject ids). Cascade: marketplace listings removed; feedback text redacted (rating and date kept); live redeem and claim codes voided; open requests cancelled; sessions and push subscriptions revoked; backups age out within 35 days (stated in the confirmation). A sole shop owner must transfer ownership or close the shop first (deletion blocked with that message). This one erasure routine backs the admin action here, self-service deletion and the public `/delete-account` page (P5-01).
- Retention purge job (daily, keyset-batched, worker role, runtime alarm, audit-logged) applying the COMPLIANCE §2 schedule: magic-link tokens 24h; sessions per role + 30 days; notifications 12 months; rejected/expired requests 24 months; feedback 24 months; game sessions 12 months; marketplace listings 30 days after end; reveal logs 12 months; device signals 90 days; receipt photos 12 months; audit logs 2 years by dropping monthly partitions only; inactive accounts flagged for review at 24 months (never auto-deleted). Categories whose tables arrive later are added by their task.
**Acceptance criteria:** deletion leaves no PII (test scans all tables for the user's email/phone/name/birthday); ledger and audit rows unchanged after deletion (same ids, same per-shop totals); feedback keeps rating and date with text redacted; export contains every category above present at this point (schema-driven test); recovery cannot complete with one admin, with the same admin approving their own request, or before 72h, and the old-email cancel link stops it; purge removes exactly the rows past their period (boundary test at period − 1 day / + 1 day) and never touches the ledger; every action audit-logged.
**Edge cases:** deletion of a sole owner (blocked); deletion with an open request or live code (voided); recovery cancelled from the old-email notice; purge job interrupted (resumes).
**Tests:** integration for deletion completeness, export scope, recovery approval and hold, purge boundaries per category.

**Acceptance criteria:**

3. k6 smoke on staging within targets: actions p95 < 300 ms, p99 < 800 ms; errors < 0.5%; queue lag < 60 s.

Launch-tier load test (15 min at 30 req/s with 1,000 SSE connections open and the 10 scans/s shop profile): actions p95 < 300 ms, p99 < 800 ms; page server time p95 < 800 ms; errors < 0.5%; queue lag < 60 s; SSE delivery p95 < 3 s. Profile and results recorded in the ARCHITECTURE capacity model and `.artifacts/`; bottlenecks fixed or logged in DECISIONS with an owner task.

6. axe: zero serious/critical violations on every page visited.

- Cross-shop isolation tested for every dashboard action; admin role matrix enforced; activation atomic; uploads hardened (P2-05, served from the `cdn.` origin); deletion complete and retention purge running; launch-tier load test recorded in the capacity model.
- Reviewer passes recorded; HUMAN_TASKS updated for P3 (Gemini paid pay-as-you-go key with a project spend cap, VAPID keys if not generated by Claude; no Google Places key and no marketing-mail setup — plan v5).

## Demo 3 script
1. A new café applies on `/join` from a phone → admin reviews, records payment, activates.
2. Owner receives the invite, signs in with 2FA, sets hours, uploads logo and cover, prints the QR poster.
3. Staff approve requests on the requests page and by scanning a member QR on a phone.
4. Customers list, segments, a customer profile, analytics for 30 days.
5. Admin: view a shop as read-only, show plan states (expiring, grace, restricted) and the audit log.
