# P2 — Shop dashboard, onboarding and admin core

**Goal:** shops can apply, be activated (with manual payment), and run their day-to-day operations; the platform team can manage shops, customers, plans and data requests safely. This phase proves multi-tenant isolation across every dashboard and admin action.

## How to work this phase
- Sub-phases A → C. Read CLAUDE.md, ENGINEERING §1, §4–6, §9–10, SECURITY §3, and each task's **Read** list.
- Every new action gets authz matrix entries in the same task. End each sub-phase with `code-reviewer` + `security-reviewer` (+ `design-reviewer` for UI), update PROGRESS + HUMAN_TASKS, commit, push.

## Sub-phase P2-A · Shop operations

### P2-01 · Dashboard home
**Depends on:** P1 complete.
**Read:** PRODUCT §14 (Overview); DESIGN §15 screen 15; reference `m15`/`d15`.
**Build:** KPI cards (visits today, gold issued today, new customers this week, offers claimed — zero until P3) with 7-day SVG sparklines; live request queue (SSE) with approve/reject inline; suggestions preview (empty state until P3); happy-hour card (placeholder until P3); weekly visits chart (chart library lazy-loaded on this route only); latest feedback (empty until P3); plan banner for `expiring | grace | restricted`. Staff see the same page minus owner-only cards (document choice in DECISIONS).
**Acceptance criteria:** KPIs use Europe/London day/week boundaries; with a 50k-row ledger seed each KPI query < 50ms (EXPLAIN evidence); queue updates live; mobile layout per screen 15.
**Tests:** unit for aggregations incl. DST day; integration for scoping (other shop's data never counted).
**Verify:** screenshots m/d; EXPLAIN output.

### P2-02 · Requests page and member QR scanning
**Depends on:** P2-01.
**Read:** PRODUCT §5, §14 (Requests); DESIGN §8.7, §15 screen 18; reference `m18`/`d18`; SECURITY §6.
**Build:**
- Tabs: Pending (incl. awaiting owner), Approved today, Expired; cursor pagination.
- Approve side panel (desktop) / sheet with large number pad (mobile): amount, item quick-picks (owner-configurable list in settings), live gold preview from the engine (incl. multipliers), receipt photo (P2-05 pipeline), reject reasons.
- Scanner: `BarcodeDetector` where available, otherwise a lazy-loaded decoder; camera permission explainer; torch toggle where supported; manual member-ID entry fallback; verifies the signed token (P1-14) and opens the award panel for that member (creates an already-approved request for audit).
- New request: row slides in with highlight; `tick` sound when the tab is focused and sounds are on.
**Acceptance criteria:** forged/expired token → clear error; scan award recorded as a request with `source=scan`; per-award limit enforced; full keyboard operation on desktop; two staff approving the same request → one succeeds, the other sees "already approved".
**Edge cases:** camera denied; poor light; member not yet joined to this shop (offer to join them? — no: show "ask the customer to scan the shop QR first"); offline counter (queue disabled with clear message).
**Tests:** integration for scan award and concurrency; E2E journey 4 with a mocked camera stream.
**Verify:** screenshots m/d; test output.

### P2-03 · Customers, segments, customer profile, export
**Depends on:** P2-01.
**Read:** PRODUCT §14 (Customers); DESIGN §15 screen 16; reference `m16`/`d16`; COMPLIANCE §2; SECURITY §2 (re-auth), §4 (CSV).
**Build:** server-paginated table (search by name, member ID, phone via blind index; sort; filter by segment); segments: Lapsed 30 days, Close to reward (≥ 75%), Top 10% by spend (rolling 90 days), New this month — implemented as tested query builders; customer profile: stats, purchase history, Vault progress, notes, "Send private offer" (enabled in P3); phone masked with reveal (logged); CSV export (owner only, TOTP re-auth, formula-injection safe, audit-logged, generated by a job and downloaded via a short-lived signed URL).
**Acceptance criteria:** only this shop's members ever appear; segment counts correct on seed data; export contains only this shop's members and only fields listed in COMPLIANCE §2.
**Tests:** integration for each segment, scoping, CSV injection; authz entries (export owner-only).

### P2-04 · Staff management
**Depends on:** P2-01.
**Read:** PRODUCT §2, §14 (Staff); SECURITY §2.
**Build:** invite by email (single-use token, 7 days), role owner/staff, per-award limit, deactivate (revokes sessions immediately), resend/revoke invite, transfer ownership (TOTP re-auth); staff must enrol TOTP before access.
**Acceptance criteria:** deactivated staff blocked on their next request; the last owner cannot be removed or demoted; invite tokens single-use and expiring.
**Tests:** integration + authz.

### P2-05 · Shop settings and upload pipeline v1
**Depends on:** P2-01; HUMAN_TASKS R2 credentials.
**Read:** PRODUCT §14 (Settings); ARCHITECTURE §8; SECURITY §8.
**Build:**
- Settings: profile, category, description, logo/cover/gallery (≤ 6) with cropper, hours editor (overnight support), closures calendar, location via postcode lookup (postcodes.io with timeout + cache) and adjustable map pin, Google Place ID (format validation + helper link), VAT number (format validation), item quick-picks, notification preferences, weekly email toggle, plan status (read-only).
- Upload pipeline: `/api/uploads` issues presigned PUT (exact type + max size) to `incoming/`; `images` job verifies magic bytes, pixel limit, decodes, re-encodes AVIF + WebP at needed sizes, strips metadata, writes to public path, updates DB, deletes original; orphan cleanup job.
**Acceptance criteria:** non-images, wrong extensions, oversized files and decompression bombs rejected; output has no EXIF/GPS (test reads metadata); replaced images cleaned up.
**Tests:** worker tests with fixtures (JPEG with GPS EXIF, PNG, HEIC, fake extension, 20k×20k, zero-byte).

### P2-06 · QR & NFC kit
**Depends on:** P2-05.
**Read:** PRODUCT §14 (QR & NFC kit); DESIGN §3–4.
**Build:** worker-generated PDFs: A5 poster and table tent (print bleed 3mm, crop marks optional), gold design, shop name/logo, QR, copy "Tap or scan to collect gold"; NFC tag status and "request replacement" (creates admin task).
**Acceptance criteria:** QR in the PDF decodes correctly (render page to image and decode in test); fonts embedded.
**Tests:** PDF render + decode test.

### P2-07 · Analytics page
**Depends on:** P2-01.
**Read:** PRODUCT §14 (Analytics).
**Build:** date range 7/30/90 days (UK time); charts: visits per day, repeat rate, gold issued vs redeemed, offer claims (P3 data), member growth; tables of top customers (owner only); CSV download of aggregates (no personal data).
**Acceptance criteria:** numbers reconcile with ledger on seed data (test compares aggregates to raw sums); queries indexed; chart library loaded only here and on dashboard home.
**Tests:** integration reconciliation tests.

## Sub-phase P2-B · Onboarding and billing

### P2-08 · Public registration page
**Depends on:** P0 complete; HUMAN_TASKS Turnstile keys.
**Read:** PRODUCT §15; DESIGN §15 screen 14; reference `m14`/`d14`; COMPLIANCE §2; SECURITY §6.
**Build:** `/join` page per screen 14 (benefits block + form card), fields per PRODUCT §15, postcode lookup, plan cards (Monthly / Lifetime), terms checkbox, Turnstile, rate limit, confirmation email, `applications` row.
**Acceptance criteria:** duplicate application from the same email within 24h → friendly "we already have your application"; no user account created until activation; all fields validated server-side.
**Tests:** integration for validation and rate limit; E2E journey 10 (first half).

### P2-09 · Applications, activation, payments, invoices
**Depends on:** P2-08.
**Read:** PRODUCT §15–16; DESIGN §15 screen 20; reference `m20`/`d20`; ARCHITECTURE §4 (applications, plans, payments, invoices).
**Build:** admin Applications list + detail (screen 20) with notes; reject with reason (email); activation in one transaction: record payment (amount, method, reference, paid date), plan (monthly/lifetime, start, expiry), create shop (code, QR, NFC tag record), owner invite, default loyalty programme from chosen template, invoice row with sequential number; after commit: invoice PDF job, emails; audit log. "Plans & payments" page: list, filter, record renewal payment (extends expiry), download invoices.
**Acceptance criteria:** activation is all-or-nothing (forced failure mid-way leaves no partial records); invoice numbers unique and sequential under concurrency; only Admin Owner/Finance can record payments.
**Tests:** integration for atomicity and numbering; authz; E2E journey 10.

### P2-10 · Plan state machine and restricted mode
**Depends on:** P2-09.
**Read:** PRODUCT §15 (plan states); ENGINEERING §8.
**Build:** pure state machine (`pending → active → expiring (≤14 days) → grace (7 days) → restricted`; `suspended` and `closed` by admin; lifetime never expires); daily job 07:00 UK applying transitions and sending reminders at 14/7/1 days (each once); dashboard banners; `assertPlanAllows(action)` used by offers, announcements, featured requests (blocked when restricted) while approvals and redemptions remain allowed.
**Acceptance criteria:** transitions at exact UK day boundaries incl. DST; reminders deduplicated; every restricted action has a test proving it's blocked server-side.
**Tests:** unit for all transitions; job tests with injected clock; E2E journey 11.

### P2-11 · Email templates
**Depends on:** P0-06.
**Read:** DESIGN §14; COMPLIANCE §3.
**Build:** React Email templates with plain-text versions: magic link, staff invite, application received / approved / rejected, activation, plan reminders, data export ready, lockout notice. Marketing-type emails (later) include one-click unsubscribe; transactional ones don't.
**Acceptance criteria:** render snapshot tests; links use the correct environment URL; no PII beyond what's necessary.

## Sub-phase P2-C · Admin core

### P2-12 · Admin shops: list, detail, suspend, close, view-as-shop
**Depends on:** P2-09.
**Read:** PRODUCT §16, §19 (shop closes); SECURITY §3, §12.
**Build:** shops list with filters (status, plan, region, category) and search; detail (profile, plan, payments, staff, KPIs); suspend/restore with reason (emails owner); close shop: members notified, rewards honoured 30 days (redemptions still allowed), then archived by job; view-as-shop: read-only session (30 min), persistent banner, every page view audit-logged.
**Acceptance criteria:** view-as-shop cannot mutate (test calls every shop action under view-as context → all FORBIDDEN); closure timeline enforced by job.
**Tests:** integration for read-only enforcement and closure lifecycle.

### P2-13 · Admin customers: lookup, recovery, data requests, blocking
**Depends on:** P2-12.
**Read:** PRODUCT §16, §17, §19 (lost access); SECURITY §7; COMPLIANCE §2.
**Build:** lookup by name, email, phone (blind index), member ID; account recovery flow for lost Google/email access (Support role; identity checks checklist recorded; changes the login email with notification to old and new address); data export (JSON + CSV via job) and deletion requests with due dates (1 month) and status; deletion anonymises: profile PII removed, phone ciphertext deleted, ledger rows re-pointed to a tombstone user, listings removed, sessions revoked; block/unblock account.
**Acceptance criteria:** deletion leaves no PII (test scans all tables for the user's email/phone/name); ledger totals per shop unchanged after deletion; every action audit-logged.
**Tests:** integration for deletion completeness and recovery.

### P2-14 · Admin QR & NFC batches
**Depends on:** P2-06.
**Read:** PRODUCT §16 (QR & NFC).
**Build:** batch-generate tag IDs and printable sheets for a shop or a batch of shops; mark tags shipped/active; replace tag (old tag URL redirects to the shop; marked replaced).
**Acceptance criteria:** replaced tag URL still lands on the right shop; sheets decode correctly.

### P2-15 · Admin team, audit log, overview, system page
**Depends on:** P2-12.
**Read:** PRODUCT §2, §16; DESIGN §15 screen 19; ARCHITECTURE §11.
**Build:** team invites and roles (Admin Owner only), 2FA status and reset (re-auth); audit log viewer (filters by actor/action/entity/date, cursor pagination, export for Owner); overview (screen 19: KPIs, applications waiting, alerts — fraud/moderation feeds added in P4 — expiring plans, activity chart, shops by region); System page: queue depths, failed jobs (retry/discard), worker heartbeat, last backup time (P5).
**Acceptance criteria:** permissions per PRODUCT §2 for each admin role; audit log complete for all P0–P2 sensitive actions (checklist test).
**Tests:** authz; integration for failed-job retry.

### P2-16 · Phase hardening
Authz coverage green for all P2 actions/routes; E2E journeys 4, 10, 11 on all projects; seed: shops in every plan state, 50k ledger rows for performance checks, pending applications; ZAP baseline dry run on staging.

## P2 definition of done
- Cross-shop isolation tested for every dashboard action; admin role matrix enforced; activation atomic; uploads hardened; deletion complete.
- Reviewer passes recorded; HUMAN_TASKS updated for P3 (AI key, VAPID keys if not generated by Claude, Google Places key if used, email domain verification for marketing mail).

## Demo 3 script
1. A new café applies on `/join` from a phone → admin reviews, records payment, activates.
2. Owner receives the invite, signs in with 2FA, sets hours, uploads logo and cover, prints the QR poster.
3. Staff approve requests on the requests page and by scanning a member QR on a phone.
4. Customers list, segments, a customer profile, analytics for 30 days.
5. Admin: view a shop as read-only, show plan states (expiring, grace, restricted) and the audit log.
