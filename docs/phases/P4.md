# P4 — Marketplace, game, moderation and fraud

**Goal:** a simple, safe marketplace that meets Online Safety Act duties; a polished mini game that can't be cheated; and the trust tooling (moderation, fraud monitor, content settings) a platform at scale needs.

## How to work this phase
- **Self-verification is part of every task:** test first for logic, run the app, inspect screenshots, try to break it (TESTING §7–8). **Close every sub-phase with `/subphase-complete`** (full regression, exploratory QA, reviews, push, CI + staging verification) and the phase with `/phase-complete`.
- Sub-phases A → C. Read CLAUDE.md, ENGINEERING §1, §4–7, COMPLIANCE §4–5, SECURITY §6, §8, and each task's **Read** list.
- End each sub-phase with `code-reviewer` + `security-reviewer` (+ `design-reviewer` for UI), update PROGRESS + HUMAN_TASKS, commit, push.

## Sub-phase P4-A · Marketplace

### P4-01 · Listings: create, browse, detail, manage
**Depends on:** P3 complete.
**Read:** PRODUCT §13; DESIGN §15 screens 9–11; reference `m09`–`m11`, `d09`–`d11`; COMPLIANCE §4.
**Build:**
- Migrations: `listings`, `listing_photos`, `listing_reveals`; DB-enforced max 3 active listings per user (trigger or locked count check); expiry 30 days.
- Create listing (screen 11): up to 5 photos (reorder, remove), title ≤ 70, description ≤ 1,000, price in pence ("Free" allowed), category (10 from content settings), contact number (encrypted), area (town or postcode district only), seller type Private/Business (Business requires business name + address shown on listing), Marketplace Rules checkbox; live preview on desktop.
- Marketplace home (screen 9): search (trigram), category row, near me by postcode-district centroid distance, 2-column mobile / 4-column desktop grid, safety banner, cursor pagination.
- Listing detail (screen 10): gallery, price, title, category, area + posted time, description, seller card (first name, seller type, member since), Reveal number (P4-03), safety tips, Report, similar nearby.
- My listings: edit, mark sold, renew (resets 30 days), delete.
**Acceptance criteria:** 4th active listing blocked by the database even under parallel creates; expired listings hidden; contact data purged 30 days after a listing ends (job); full address never requested or displayed for private sellers.
**Tests:** integration for limits (parallel), expiry and purge jobs; E2E create → pending review.
**Verify:** screenshots m/d; test output.

### P4-02 · Upload pipeline hardening and CDN origin
**Depends on:** P2-05.
**Read:** SECURITY §8; ARCHITECTURE §8.
**Build:** separate `cdn.` origin serving only processed images with correct `Content-Type`, `X-Content-Type-Options: nosniff`, no HTML/SVG; pixel and frame limits (reject animated); HEIC conversion; per-user daily upload quota; orphaned `incoming/` cleanup job.
**Acceptance criteria:** fixture suite passes: polyglot file, SVG, animated GIF/WebP, 20k×20k PNG, JPEG with GPS EXIF (stripped), truncated file, wrong extension; nothing served from the CDN can execute script.
**Tests:** worker fixture tests; header check on CDN responses.

### P4-03 · Reveal number, seller types, 18+ confirmation
**Depends on:** P4-01.
**Read:** PRODUCT §13; COMPLIANCE §4, §7; SECURITY §6.
**Build:** Reveal number for signed-in users with 18+ confirmed: 20/day, Turnstile after 5, each reveal logged; seller can hide the number at any time; 18+ confirmation (year + month of birth check, stored as boolean + date, birth date not stored) before first listing or first reveal; under-18 path blocks marketplace actions with a friendly message.
**Acceptance criteria:** 21st reveal in a day blocked; number never present in HTML until revealed (server returns it only via the reveal action); hidden numbers can't be revealed.
**Tests:** integration for limits, gating and hidden numbers.

### P4-04 · Moderation: keywords, pre-moderation, reports, actions, appeals, strikes
**Depends on:** P4-01.
**Read:** COMPLIANCE §4; PRODUCT §13, §16.
**Build:**
- Prohibited keyword list (content settings) with normalised matching (case, accents, leetspeak like "v4pe", spacing tricks) → listing held for review with matched term recorded.
- First 3 listings of a new seller pre-moderated.
- Reports on listings, sellers, feedback and offer banners: reason categories + free text; reporter gets an acknowledgement with expected timeframe (24h).
- Moderation queue (Moderator role): SLA timers, filters, item context, actions approve / remove with reason / warn / suspend; seller notified with reason and appeal link; appeals queue reviewed by a different moderator where possible; strikes (3 upheld → suspension); everything in `moderation_actions` + audit log.
- Admin overview alerts now fed by moderation counts.
**Acceptance criteria:** every report acknowledged; every removal has a reason; suspended sellers' listings hidden immediately; keyword matcher catches the obfuscation fixtures without obvious false positives (fixture list of allowed words like "vapour barrier" documented).
**Tests:** unit for matcher; integration for flows; E2E journey 9.

### P4-05 · Marketplace legal drafts and OSA risk-assessment template
**Depends on:** P4-04.
**Read:** COMPLIANCE §4, §8.
**Build:** `src/content/legal/` drafts marked "Draft — requires legal review": Marketplace Rules, Prohibited Items, Reporting and Complaints; render at `/legal/*`; `docs/legal-templates/osa-risk-assessment.md` prefilled with the platform's features, risks and controls for the client to complete; HUMAN_TASKS item for solicitor review.

## Sub-phase P4-B · Mini game

### P4-06 · Stack the Gold game
**Depends on:** P0-10, P0-11.
**Read:** PRODUCT §12; DESIGN §8 principles, §12 (game budget); COMPLIANCE §5; `animation-performance`, `mobile-native` skills.
**Build:** lazy route; pure step function (state, input, dt) → state for testability; canvas renderer with DPR scaling; rAF loop paused when hidden; `pointerdown` input for minimal latency; bar slides, overlap kept, overhang sliced and falls; speed curve; sounds and haptics via existing modules; start screen (best score, weekly rank), game over (score, best, play again, share); practice vs rewarded play (shop picker from joined shops).
**Acceptance criteria:** 60 fps on a 4× throttled profile; no memory growth across 10 consecutive games (heap snapshot comparison); playable one-handed at 320px; reduced motion keeps it playable with simplified effects; chunk ≤ 40 KB gzip.
**Tests:** unit tests for the step function (overlap, slicing, game over, speed); Playwright smoke (start, taps, game over).
**Verify:** `animation-performance` pass; performance trace screenshot.

### P4-07 · Leaderboards, game rewards, anti-cheat
**Depends on:** P4-06.
**Read:** PRODUCT §12; SECURITY §6; COMPLIANCE §5.
**Build:** server-issued game session (id, start time, seed) single-use; score submission validated (minimum duration per score, maximum stacking rate, session age, seed-consistent); weekly leaderboard per shop (first name + initial; resets Monday 00:00 UK); optional shop reward at a score threshold, once per day per shop, capped at 10 rewarded plays per day per user; `bonus_game` ledger entry; game reward settings in the Loyalty programme page.
**Acceptance criteria:** replayed, forged or too-fast submissions rejected and flagged; nothing in the flow costs money or points to play (reviewer checklist).
**Tests:** integration for validation, caps and weekly reset.

## Sub-phase P4-C · Trust and platform settings

### P4-08 · Fraud monitor
**Depends on:** P1-12, P3-11, P4-07.
**Read:** PRODUCT §16 (rules), §19; SECURITY §1, §6.
**Build:** rule jobs after awards, scores and referrals: award > 3× shop average; > 10 awards/day to one customer; one staff member awarding the same customer > 5×/week; many accounts per device hash; game scores failing plausibility; referral abuse; request far outside shop area (only when the customer voluntarily granted location for Near me in that session — never required). Flags with evidence, severity, status; admin UI (filters, detail, actions: dismiss, reverse award, suspend staff/customer, contact shop); alerts for high severity; overview alerts fed.
**Acceptance criteria:** every rule has positive and negative unit tests; seed triggers at least one flag per rule.
**Tests:** unit per rule; integration for actions.

### P4-09 · Content settings and broadcasts
**Depends on:** P4-04.
**Read:** PRODUCT §16.
**Build:** admin editors: marketplace categories, prohibited keywords (+ allowed exceptions), review chips, banner template texts, game settings; changes apply without deploy (cache invalidation); broadcasts to all shops (email + dashboard banner) with preview, scheduling, audit log.
**Acceptance criteria:** editing a chip list updates the review sheet within one cache cycle; broadcasts reach only active shops.
**Tests:** integration for invalidation and targeting.

### P4-10 · Phase hardening
Authz coverage green; E2E journey 9 (with unhappy paths) plus full regression of all earlier journeys on all projects; mutation testing on fraud rules and game score validation; ZAP baseline with findings fixed or logged; seed: listings in each category, a held prohibited item, open reports and an appeal, fraud flags per rule, leaderboard data; reviewer passes.

## Demo 5 script
1. List a bike with photos → held as a first listing → moderator approves → buyer reveals the number.
2. Try listing a vape → held automatically; report a listing → moderator removes with reason → seller sees the appeal link.
3. Play Stack the Gold on a phone → appear on the shop's weekly leaderboard; show a rejected forged score in the fraud monitor.
4. Reverse a suspicious award from a fraud flag.
