# P4 — Marketplace, game, moderation and fraud

**Goal:** a simple, safe marketplace that meets Online Safety Act duties; a polished mini game that can't be cheated; and the trust tooling (moderation, fraud monitor, content settings) a platform at scale needs.

**Target date:** Sat 2 Jan 2027 (plan v5 re-baseline; assumptions in PHASES.md and PROGRESS).

## How to work this phase
- **Before the first task of this phase**, run a brief review: fill any missing Edge cases and measurable Acceptance criteria in this file (one agent, cheap; commit with the first task).
- **Self-verification is part of every task:** test first for logic, run the app, inspect screenshots, try to break it (TESTING §7–8).
- **Task:** `pnpm gate:task` only (check + test:int + build + the task's E2E specs on the production build, Chromium + WebKit). No full regression, no exploratory QA agent, no all-project runs. Tasks touching auth, authz, sessions, rate limits, payments, uploads, crypto or PII run `security-reviewer` on the task diff before the tick.
- **Sub-phase close (`/subphase-complete`) is light:** CI green on the last commit (CI already ran the full suite; do not re-run it locally); staging deploy + smoke + Sentry check; `code-reviewer` (+ `security-reviewer` for server/auth code, `design-reviewer` for UI) on commits not already reviewed at task tick; exploratory QA only if the sub-phase added or changed screens, scoped to those screens at 320/390/1440 on Chromium + WebKit; update PROGRESS + HUMAN_TASKS; push.
- **Phase close is the one heavy gate:** `pnpm gate:phase` + definition of done + demo. P4-10 IS that run; `/phase-complete` does not repeat it. Demo for P4: screenshot walkthrough of the Demo 5 script (no recorded rehearsal).
- The marketplace stays behind the `marketplace` feature flag until P4-05's rules, prohibited-items and reporting pages are live; they ship in this phase, not P5.
- Sub-phases A → C. Read CLAUDE.md, ENGINEERING §1, §4–7, COMPLIANCE §4–5, SECURITY §6, §8, and each task's **Read** list.

## Sub-phase P4-A · Marketplace

### P4-01 · Listings: create, browse, detail, manage
**Depends on:** P3 complete.
**Read:** PRODUCT §13; DESIGN §15 screens 9–11; reference `m09`–`m11`, `d09`–`d11`; COMPLIANCE §4.
**Build:**
- Migrations: `listings`, `listing_photos`, `listing_reveals`; DB-enforced max 3 active listings per user (trigger or locked count check); expiry 30 days.
- Create listing (screen 11): up to 5 photos (reorder, remove), title ≤ 70, description ≤ 1,000, price in pence ("Free" allowed), category (10 from content settings), contact number (encrypted), area (town or postcode district only), seller type Private/Business (Business requires business name + address shown on listing), Marketplace Rules checkbox; live preview on desktop.
- Marketplace home (screen 9): search (trigram), category row, near me by postcode-district centroid distance, 2-column mobile / 4-column desktop grid, safety banner, cursor pagination.
- Listing detail (screen 10): gallery, price, title, category, area + posted time, description, seller card (first name, seller type, member since), Reveal number (P4-03), safety tips, Report, similar nearby.
- Seller profile: first name, seller type, member since, active listings; Report and Block actions. Blocking hides the blocked seller's listings from the blocker and stops either side revealing the other's number; unblock from Me.
- Photos go through the P2-05 pipeline (EXIF/GPS stripped, served from the `cdn.` origin).
- My listings: edit, mark sold, renew (resets 30 days), delete.
- Listing rows and contact data join the P2-13 retention purge (30 days after end) and DSAR export.
**Acceptance criteria:** 4th active listing blocked by the database even under parallel creates; expired listings hidden; contact data purged 30 days after a listing ends (job); full address never requested or displayed for private sellers; creating a listing without 18+ confirmation rejected server-side (P4-03); blocked seller's listings absent from the blocker's home, search and similar-nearby results.
**Tests:** integration for limits (parallel), block filtering, expiry and purge jobs; E2E create → pending review; E2E seller profile Report and Block.
**Verify:** screenshots m/d; test output.

### P4-02 · Per-user upload quota
**Depends on:** P2-05 (the hardened pipeline and `cdn.` origin already exist; this task adds only the quota).
**Read:** SECURITY §8; ARCHITECTURE §8.
**Build:** per-user daily upload quota (count and bytes, values from SECURITY §8, UK day) enforced when `/api/uploads` issues the presigned PUT; friendly limit message; counted atomically in Redis (`redis-queue`, fails closed).
**Acceptance criteria:** the upload after the quota in a UK day is refused before any presigned URL is issued; parallel requests cannot exceed the quota; quota resets at UK midnight; shop staff uploads (P2-05 settings) use their own limit.
**Tests:** integration for quota (parallel, reset with injected clock, Redis down → refused).

### P4-03 · Reveal number, seller types, 18+ confirmation
**Depends on:** P4-01.
**Read:** PRODUCT §13; COMPLIANCE §4, §7; SECURITY §6.
**Build:** Reveal number for signed-in users with 18+ confirmed: 20/day, Turnstile after 5, each reveal logged; seller can hide the number at any time; 18+ confirmation (year + month of birth check, stored as boolean + date, birth date not stored) before first listing or first reveal; under-18 path blocks marketplace actions with a friendly message.
**Acceptance criteria:** 21st reveal in a day blocked; number never present in HTML until revealed (server returns it only via the reveal action); hidden numbers can't be revealed; both listing creation and reveal are refused server-side without 18+ confirmation; reveal between blocked users refused; reveal logs join the P2-13 retention purge (12 months) and DSAR export.
**Tests:** integration for limits, 18+ gating on listing and reveal, block, and hidden numbers.

### P4-04 · Moderation: keywords, pre-moderation, reports, actions, appeals, strikes
**Depends on:** P4-01.
**Read:** COMPLIANCE §4; PRODUCT §13, §16.
**Build:**
- Prohibited keyword list (content settings) with normalised matching (case, accents, leetspeak like "v4pe", spacing tricks) → listing held for review with matched term recorded.
- First 3 listings of a new seller pre-moderated.
- Reports on listings, sellers (from the seller profile), feedback and offer banners: reason categories + free text; the reporter gets an acknowledgement at once (on screen and in the inbox) stating the review timeframe (24h), and a notice of the outcome.
- Moderation queue (Moderator role): SLA timers, filters, item context, actions approve / remove with reason / warn / suspend; seller notified with reason and appeal link; appeals queue reviewed by a different moderator where possible; strikes (3 upheld → suspension); everything in `moderation_actions` + audit log.
- Admin overview alerts now fed by moderation counts.
**Acceptance criteria:** every report acknowledged immediately with the 24h timeframe stated, and the reporter told the outcome; every removal has a reason; suspended sellers' listings hidden immediately; keyword matcher catches the obfuscation fixtures without obvious false positives (fixture list of allowed words like "vapour barrier" documented).
**Tests:** unit for matcher; integration for flows; E2E journey 9.

### P4-05 · Marketplace legal drafts and OSA risk-assessment template
**Depends on:** P4-04.
**Read:** COMPLIANCE §4, §8.
**Build:** `src/content/legal/` drafts marked "Draft — requires legal review": Marketplace Rules, Prohibited Items, Reporting and Complaints (incl. the 24h acknowledgement timeframe and appeals); render at `/legal/*`; linked from the create-listing checkbox, listing detail, seller profile, report sheet and footer; `docs/legal-templates/osa-risk-assessment.md` (illegal-content and children's-access assessments) prefilled with the platform's features, risks and controls for the client to complete; HUMAN_TASKS item for solicitor review.
**Acceptance criteria:** all three pages live on staging and linked from every marketplace entry point listed (E2E link check); the `marketplace` flag cannot be enabled in production while any of the pages is missing (startup or flag-toggle check).

## Sub-phase P4-B · Mini game

### P4-06 · Stack the Gold game
**Depends on:** P0-10, P0-11.
**Read:** PRODUCT §12; DESIGN §8 principles, §12 (game budget); COMPLIANCE §5; `animation-performance`, `mobile-native` skills.
**Build:** lazy route; pure step function (state, input, dt) → state for testability; canvas renderer with DPR scaling; rAF loop paused when hidden; `pointerdown` input for minimal latency; bar slides, overlap kept, overhang sliced and falls; speed curve; sounds and haptics via existing modules; start screen (best score, weekly rank), game over (score, best, play again, share); practice vs rewarded play (shop picker from joined shops).
**Acceptance criteria:** 60 fps on a 4× throttled profile; no memory growth across 10 consecutive games (heap snapshot comparison); playable one-handed at 320px; reduced motion keeps it playable with simplified effects; chunk ≤ 40 KB gzip.
**Tests:** unit tests for the step function (overlap, slicing, game over, speed); Playwright smoke (start, taps, game over).
**Verify:** `animation-performance` pass; performance trace screenshot.

### P4-07 · Leaderboards, game rewards, anti-cheat
**Depends on:** P4-06.
**Read:** PRODUCT §12; SECURITY §6; COMPLIANCE §5.
**Build:** server-issued game session (id, start time, seed) single-use; score submission validated (minimum duration per score, maximum stacking rate, session age, seed-consistent); weekly leaderboard per shop (first name + initial; resets Monday 00:00 UK); optional shop reward at a score threshold, once per day per shop, capped at 10 rewarded plays per day per user; `bonus_game` ledger entry; game reward settings in the Loyalty programme page.
**Acceptance criteria:** replayed, forged or too-fast submissions rejected and flagged; nothing in the flow costs money or points to play (reviewer checklist).
**Tests:** integration for validation, caps and weekly reset.

## Sub-phase P4-C · Trust and platform settings

### P4-08 · Fraud monitor
**Depends on:** P1-12, P3-11, P4-07.
**Read:** PRODUCT §16 (rules), §19; SECURITY §1, §6.
**Build:** rule jobs after awards, scores and referrals, triggered through the outbox (P1-12 already writes the fraud-check row): award > 3× shop average; > 10 awards/day to one customer; one staff member awarding the same customer > 5×/week; many accounts per device hash; staff awarding an account seen on the same device (P1-12 flag); game scores failing plausibility; referral abuse; request far outside shop area (only when the customer voluntarily granted location for Near me in that session — never required). Rules read incremental aggregates (rolling shop average, per customer/day, per staff-customer/week, per device-hash counters) updated by the same job — never a scan of the ledger or full tables. Flags with evidence, severity, status; admin UI (filters, detail, actions: dismiss, reverse award, suspend staff/customer, contact shop); alerts for high severity; overview alerts fed. Device signals used only for fraud and security (90-day retention via P2-13 purge).
**Acceptance criteria:** every rule has positive and negative unit tests; seed triggers at least one flag per rule; flag raised p95 < 60 s after the triggering award on staging; rule evaluation cost independent of ledger size (EXPLAIN shows index/aggregate lookups only, measured at 50k and 500k ledger rows); aggregates rebuilt correctly after a replayed job (idempotent).
**Tests:** unit per rule; integration for aggregates (idempotent replay), latency and actions.

### P4-09 · Content settings and broadcasts
**Depends on:** P4-04.
**Read:** PRODUCT §16.
**Build:** admin editors: marketplace categories, prohibited keywords (+ allowed exceptions), review chips, banner template texts, game settings; changes apply without deploy (cache invalidation); broadcasts to all shops (dashboard banner + shop staff inbox; never email — plan v5 email budget) with preview, scheduling, audit log.
**Acceptance criteria:** editing a chip list updates the review sheet within one cache cycle; broadcasts reach only active shops and write no email outbox rows.
**Tests:** integration for invalidation and targeting.

### P4-10 · Phase hardening
**Depends on:** all P4 tasks.
**Build:** this task IS the phase-close run (`/phase-complete` adds only DoD and demo). Seed: listings in each category, a held prohibited item, open reports and an appeal, a blocked seller, fraud flags per rule, leaderboard data.
**Acceptance criteria:**
1. `pnpm gate:phase` green: 5 projects incl. E2E journey 9 with unhappy paths plus all earlier journeys; `test:live --require-all` on staging; summary saved to `.artifacts/` and one line in SESSION_LOG.
2. Authz coverage green for all P4 actions and routes (moderator, seller, buyer, admin).
3. k6 smoke on staging (marketplace home, listing detail, reveal, game score submit, approvals) within targets: actions p95 < 300 ms, p99 < 800 ms; errors < 0.5%; queue lag < 60 s.
4. Mutation score ≥ 80% on changed rules modules: fraud rules, game score validation, keyword matcher, listing and reveal limits.
5. axe: zero serious/critical violations on every page visited.
6. Lighthouse on marketplace home, listing detail and the game route meets DESIGN §12 targets (incl. the game budget; or within the judgment rule with a DECISIONS entry).
7. Rollback rehearsal on staging: deploy N, roll back to N-1, smoke passes.
8. RUNBOOK extended for P4: moderation backlog and SLA breach, illegal-content takedown, fraud high-severity response, game exploit response, marketplace kill switch.
9. Latest weekly ZAP baseline reviewed (no unresolved high/medium).
10. Demo: screenshot walkthrough of the Demo 5 script on staging (no recorded rehearsal).

## P4 definition of done
- Marketplace moderation and reporting complete with records; rules, prohibited-items and reporting pages live; seller Report and Block working; 18+ enforced for listing and reveal; per-user upload quota enforced; game unexploitable by replay/forgery; fraud rules tested within the latency bound.
- HUMAN_TASKS: solicitor review of marketplace drafts; client to complete OSA risk assessment.

## Demo 5 script
1. List a bike with photos → held as a first listing → moderator approves → buyer reveals the number.
2. Try listing a vape → held automatically; report a listing → moderator removes with reason → seller sees the appeal link.
3. Play Stack the Gold on a phone → appear on the shop's weekly leaderboard; show a rejected forged score in the fraud monitor.
4. Reverse a suspicious award from a fraud flag.
